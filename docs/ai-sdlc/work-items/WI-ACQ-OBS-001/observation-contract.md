## O1 — hook and durability classes
Every implemented/future capability requires the common hook AND versioned manifest before activation, including nonpayment auxiliary capabilities; no future operation is commissioned. A manifest declares tasks, conditional branches, producers, critical-transition budget, and durability class. Initial A includes receive, context-check, validate, idempotency-check, request-adapt, dispatch, response-adapt, business-persist, channel-response; network/issuer tasks only where observed.
CRITICAL_COMMITTED: event from committed business change, atomically durable with journal/evidence/head updates. Business claim, possible-send and verified result/late result are not inferred from tasks.
TASK_BEST_EFFORT: every task invokes started/terminal hook where observable; nonblocking per-invocation memory queue <=100 events/200KiB, asynchronous writer inserts directly into SAME event table. No separate history copy, no awaiting queue delivery before payment. Queue, invocation/crash and async Lambda retry limits can lose events. Missing preauth/start/terminal/producer observations remain explicit gaps; missing event is NOT FAILED. Proposed async writer within query/notifier responsibility, service-scoped async Invoke, maximum age1h/retries2 subject to runtime/IAM preflight. It cannot write business state or fabricate critical class.
TECHNICAL_SAMPLED: separate ADOT/OTel spans/metrics/safe logs asynchronously exported to configured AWS destinations. Sampling/drop/lifecycle/resource overhead remain; never proves task completeness or financial result. A received span cannot replace a lost functional event.
Preauth observations before business claim have no guaranteed durable transaction identity; use separate safe request metadata only where observed, never attach by guessed foreign correlation. Source redaction is mandatory: no raw ISO, attestation/signature, JWT, credentials, PAN/PIN/EMV/3DS blobs, arbitrary logs/error bodies in event table, ADOT or failure destinations. No zero-cost full per-task durability claim.

## O3 — atomic DynamoDB business + queryable event, no dual write
Before send, one transaction creates/updates mandatory business record, idempotency generation/head, critical event itself, event HEAD/dedupe and slot accounting. No business-write-then-event-write; no PostgreSQL/DynamoDB dual write; no second event payload copied for history or notification. A failed transaction changes neither business state nor critical event. Ambiguous commit -> strongly consistent lookup of stable transition token/business/event before any send; inability to establish state means UNAVAILABLE, not proof of no-send.
CLAIMED_NOT_SENT may progress only in its ORIGINAL running invocation through atomic POSSIBLE_SEND+critical event before invoking downstream once. Event-store failure on this required atomic write is business-admission failure, not async backend failure. Retry/restart of old claim NEVER resumes sending; future notification workers cannot perform the financial CAS. A crash after POSSIBLE_SEND before actual invocation is deliberately possible-send uncertainty.
P5/C4 authenticated, correlated verified issuer evidence becomes processor-known only when evidence+business version+critical consultable event commit atomically. Late evidence uses same internal admission; no public late endpoint/automatic financial recovery. Event/history/task/span alone cannot admit payment result.
HTTP payment result uses readable journal (or committed version read in current invocation), not event-table history as fresh financial authority. A signed but uncommitted reply, issuer-only table read or disconnected green UI is not confirmation.
Notifier/ADOT/management callback/connection table outage by itself does not block payment. Async intermediate writer outage loses or delays tasks, not payment. Required business+critical event transaction outage before send prevents send; after possible send current invocation returns conservative NOT_CONFIRMED unless prior committed result readable, unreadable restart UNAVAILABLE. No auto payment resend, rollback, reversal or inquiry. Existing key, prior precedence and24h generation rules unchanged.

Keys/cursors are opaque to browser.

Deduplicate producer/eventId+hash and sourceSequence; same ID/sequence different content -> explicit integrity gap, do not overwrite. Emit contiguous source order; receiving sequence N+1 with N missing triggers source catch-up, not fabricated event.
