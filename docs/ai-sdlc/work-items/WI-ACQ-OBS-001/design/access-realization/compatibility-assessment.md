## 1. Presenter relay and relay→console hops versus mTLS + OAuth access token + separate demo context

**What exists.** The only HTTP surface is a SAM `AWS::Serverless::HttpApi` (`infra/template.yaml:47-60`) with a native JWT authorizer (`TestJwt`, identity source `$request.header.Authorization`, issuer/audience from parameters) and one route, `POST /authorizations` (`:79-86`). `ProcessorHandler` accepts only payload `2.0`, `POST`, `rawPath=/authorizations` (`ProcessorHandler.java:30-33`), reads exactly one identity input — `requestContext.authorizer.jwt.claims.sub` (`:35`) — and resolves the mandate through `AwsRuntime.caller(subject)` → a `CALLER#<subject>` / `PROFILE` item in `JOURNAL_TABLE` (`AwsRuntime.java:28-43`). An unknown or blank subject is `403`, never a body-supplied context (`AwsTransportTest.unauthenticatedOrUnregisteredCallerCannotSupplyTheirOwnContext`, `authenticatedInputUsesTrustedRegistryAndReturnsOnlyOutcomeAndReference`).

**What does not exist.** There is no relay process, no loopback HTTP server, no session/CSRF/Host/Origin handling, no `X-Demo-JWT`, no second audience, no custom domain, no truststore, no mTLS setting, and no service-vs-demo token separation anywhere in `src/` or `infra/`. A case-insensitive grep for `mtls|mutualTls|private_key_jwt|client_assertion|X-Demo-JWT` over both trees returns no match.

**Assessment.**

1. **The identity model is one-plane in code and three-plane in the proposal.** The proposal's P-TLS + P-SVC + P-DEMO triplet (§2, §6 S2) requires three independent inputs at the hop. The implemented hop consumes one (Gateway-validated `sub`) and maps it to a registry row. The registry row type, `AuthorizedContext(acquirerRef, merchantRef, callerId, permittedRoutes)`, cannot represent the proposal's §5 record: no `client_id`, no `env`, no `certFingerprints[]`, no `contexts[]`, no `role`, no `c4KeyIds[]`. So the proposal's "certificate must map to that same client" and "claims are hints, the registry is authoritative" have no data model today.
2. **mTLS is not a switch on the current authorizer.** A native JWT authorizer validates a token; it cannot recompute a leaf-certificate fingerprint or compare token `client_id` to a certificate-bound client. The proposal's §5 check order and §4 TTL-0 rule therefore imply replacing `TestJwt` with a request (Lambda) authorizer on mTLS routes — an authorizer-type change, not a property addition. The current SAM resource has no `Domain`/`MutualTlsAuthentication`/`DisableExecuteApiEndpoint` at all.
3. **Two-layer validation is currently one layer.** Proposal §4.2 requires the application to re-check signature/issuer/expiry/audience/scope. `ProcessorHandler` re-checks none of these; it trusts the Gateway claims. Payload v2 does forward the `Authorization` header in `event.headers`, so application revalidation is implementable, but nothing in the checkout does it. The deny cases "service token at demo route" and "demo token at service route" are therefore untestable today: with one audience there is no distinction to deny.
4. **The console route in the approved contract is absent.** C1 names `POST /console/v1/authorizations` with a 4096-byte JSON body and a specific field set (`channel-contract.md:5`). The implemented route is `POST /authorizations` with a different body model (`PurchaseRequest`, `WireJson.read`). A relay pointed at the current route would be speaking the wrong contract, and a relay pointed at the contract route would get `404` from `ProcessorHandler` and no route from the Gateway.
5. **Spoofed identity headers are already refused — but only on the internal adapter.** `HttpApiV2Wire.refuseIdentityAssertions` rejects `x-authenticated-sender`, `x-simulator-principal`, `x-remote-user` and peers (`HttpApiV2Wire.java:51-57,154-161`), proven by `HttpApiV2InternalRouteTest.forgedIdentityHeadersCannotCreateTrustedSender`. That adapter is not wired to the console route, so the property does not protect the relay→console hop yet.

**Verdict: directionally compatible, not realizable by configuration.** It needs a new authorizer/registry model, a second audience/header with enforcement, and a relay component. No approved contract is contradicted by the *direction*; the gap is that the proposal describes three controls where the checkout has one.

## 2. C4 late evidence and Ed25519 signing versus Gateway header/body limits

**Declared bounds (source).** Normal carriage: one `X-Simulator-Evidence` header, `MAX_ENCODED_CHARS=5464`, `MAX_DECODED_BYTES=4096`, `MAX_BODY_BYTES=2048`, `MAX_TOTAL_HEADER_BYTES=8192` (`C4CarrierParser.java:41-56`). Late delivery: raw envelope `8192`, decoded original body `2048`, nested evidence `4096`, receipt id `64` (`C4LateDeliveryParser.java:36-45`). Both are enforced before parsing and are covered by tests: `C4CarrierParserTest.boundsAreEnforcedBeforeDecode` (5468 encoded → `CARRIER_SIZE`; 5464 encoded of padding → `CARRIER_SIZE` after decode), `totalHeaderBudgetAndBodyBudgetAreEnforced` (8193 total headers → `HEADERS_TOO_LARGE`; 2049 body → `BODY_SIZE`), `C4LateDeliveryTest.oversizedLateEnvelopeIsRejectedBeforeParsing` (8193 → `LATE_ENVELOPE_SIZE`), `oversizedOriginalBodyIsRejected`.

**Computed worst case from the attested field bounds** (`C4EvidenceAttestation.java:75-105`), canonical RFC8785 order, printable ASCII, all values at their declared maxima:

| Object | Canonical bytes | Base64 chars | Headroom to local bound |
| --- | --- | --- | --- |
| Attestation, all 31 keys at max | 503 | n/a | n/a |
| DIRECT envelope (incl. 88-char signature) | 738 | 984 | 3358 bytes / 4480 chars |
| RELAY envelope (incl. 555-byte relay object) | 1288 | 1720 | 2808 bytes / 3744 chars |
| Late envelope, DIRECT worst | 3606 | n/a (JSON body) | 4586 bytes |
| Late envelope, RELAY worst | 4156 | n/a (JSON body) | 4036 bytes |
| Late envelope at the 4096 evidence cap | 6964 | n/a | 1228 bytes |

**Assessment: the payload fits; identifier indirection is not required on size grounds.** Three qualifications matter more than the fit itself:

1. **The header limit question attaches to the normal response, not to late admission.** The late path carries canonical JSON in the **body** (`C4LateDeliveryEnvelope`/`C4LateDeliveryParser`), so Gateway per-header limits do not apply to its evidence at all. Proposal §15.5 frames the C4 header quota as a risk to "the C4 envelope (`X-Simulator-Evidence`) on the chosen API type" — correct for the normal 200 response, mis-scoped if read as a late-path blocker. The late path's real ceiling is the 8192-byte body bound.
2. **The late envelope is the tightest artifact in the system — and its worst case is not the binding one.** The all-maxima RELAY late envelope is 4156 bytes, about half the 8192 ceiling. The binding case is a late delivery whose inner evidence uses its full 4096-byte allowance: 6964 bytes, only 1228 bytes (~15%) below the limit. Any future increase to the original-body cap, the evidence cap, or the receipt-id cap erodes that margin; a design that later needs a larger error/reason vocabulary, or an added top-level late field, must re-derive the number rather than assume it.
3. **The proposal's own residual stands.** No AWS page in the reviewed evidence asserts a per-header cap above ~1.7 KB, and the proposal deliberately does not assert the quota (§15.5). Locally the RELAY maximum needs a single header value of 1720 characters and 1818 bytes of total headers — an order of magnitude below the general API payload ceiling but **unverified** against the current quota page. Identifier indirection would become necessary only if the chosen API type enforces a per-header value cap below ~1.8 KB or a total-header cap below ~2 KB. Nothing observed suggests that; nothing observed proves the opposite either.

One structural note the proposal does not state: the app-side 8192 check sums only the headers the application supplies (`HttpApiV2Wire.totalHeaderBytes`, `HttpApiV2Wire.java:218-226`). A deployed Gateway response also carries platform headers (at minimum a request id), so the on-wire total exceeds the app-computed total. With 1818 bytes used, the ~6.3 KB slack absorbs it; a payload near the 8192 ceiling would not.

## 3. WebSocket connect-only authorizer, per-frame revalidation and catch-up versus `lease = min(JWT exp, 30 min)`

**What exists.** Nothing executable. `infra/template.yaml` has no `AWS::ApiGatewayV2::Api` of type `WEBSOCKET`, no `$connect`/`$disconnect`/`$default` route, no connection store, no notifier, no `@connections` policy, and no catch-up route. A case-insensitive grep for `websocket|$connect|connectionId` over `src/` and `infra/` returns one documentation sentence in `ObsAcceptanceAtomicChainIntegrationTest` (OBS-20: payment correctness holds with no notifier/WebSocket/query). `vectors/websocket-vectors.json` is explicitly a bundle of **PROPOSED future QA inputs**, not executed behaviour.

**Assessment.**

1. **The connect-only authorizer is a platform property, and the proposal states it correctly.** Because Gateway authenticates only `$connect` (`design.md` §8 cites the AWS page), per-frame revalidation must live in the `$default` integration. That integration requires a per-connection record with `{connectionId, epoch, clientId, demoSubject, env, jwtExp, leaseExpiry, registryVersion}`. The current persistence model has no such partition: `EventTableKeys` defines event, HEAD, dedupe and capacity partitions only (`EventTableKeys.java:23-66`), and `EventStore` exposes `append`, `find`, `head` (`EventStore.java`) — no connection entity. This is a new table or a new partition plus a new adapter, not a reuse.
2. **The lease arithmetic is internally dead.** The proposal sets access tokens ≤900 s (§3.3) and a lease of `min(jwtExp, now+30 min)` (§8.3). With a ≤15-minute token, `jwtExp` is always the minimum, so the 30-minute term can never bind. The 30-minute number only becomes meaningful if the access-token lifetime is raised above 30 minutes — which §3.3 forbids. This is not a contradiction with an approved contract (`C6`/O4 also say `min(JWTexp, lease)`), but the constant should be reconciled rather than carried as if it were a second control.
3. **Lease outlives the catch-up cursor.** C7 bounds the signed catch-up cursor to 15 minutes (`channel-contract.md`, C7) while the connection lease may reach 30 minutes on paper. A socket that survives past cursor expiry must re-mint a cursor before its next catch-up; the proposal does not say so. With the ≤15-minute token the two horizons coincide, which masks the issue until the token policy changes.
4. **Revocation-on-next-frame requires a registry read per frame, and the current registry is cold-start cached.** `AwsRuntime.caller` reads `CALLER#…` once per cold start via a static holder (`AwsRuntime.java:15,28-43`), with no revocation status, no version, and no TTL. The proposal requires revocation to close a connection "at the next frame or heartbeat" but says nothing about caching the registry lookup that detects it. Without a decision, either every frame does a strongly consistent DynamoDB read (latency and cost on the notification path) or revocation is delayed by the cache — a residual that Security must see, because D-D accepted this path precisely on the strength of per-frame revalidation.
5. **Catch-up has no reader.** C7 requires `GET /console/v1/transactions/{id}/events` with `snapshotHead`, `expiryRevision`, `firstRetainedSequence`, `events`, `coveredThrough`, `expiredRanges`, `gapRanges`, `nextCursor` and a signed 15-minute cursor. No such route or reader exists, and `EventStore` has no range/after-cursor operation. `AuthorizationService.history(authorizationId)` reads the journal repository, not the event table (`AuthorizationService.java:479-481`), so it cannot serve event-source catch-up. The proposal's reconnect story therefore depends on a port that has not been written.
6. **The payment-path independence claim holds today.** `AuthorizationService.authorize`/`authorizeAtomic`/`sendDownstream` never reference a notifier, socket or query API (`AuthorizationService.java:239-260, 566-650`), and `LambdaDownstream` has no notification hook. So D-D's "losing the WebSocket must not block an HTTP payment" is trivially true in the current code, and must be preserved as an invariant when the WS path is added — not proven by it.

**Verdict: no conflict with existing code, because the code is absent; the proposal is a net-new subsystem whose two numeric controls (30-minute lease, 15-minute cursor) need reconciliation and whose registry-read cost needs a stated cache policy.** D-D is respected: transport assurance is knowingly weaker on this path, scope is notification-only.

## 4. Internal Lambda-to-Lambda hops under IAM-only authorization versus the current internal contract

**What exists.** `LambdaDownstream.decide` issues one `InvokeRequest` with `REQUEST_RESPONSE`, the JSON `SimulatedDecisionRequest` payload, and an `apiCallTimeout` equal to the business response timeout (`LambdaDownstream.java:16-24`). `AwsRuntime.createLambda` sets `RetryPolicy.none()` and a 4 s client timeout (`AwsRuntime.java:19-22`). Any SDK error, non-200, `functionError`, missing payload or parse failure becomes `DownstreamReply(NO_RESPONSE)` — unknown, never a decline, never a retry (`LambdaDownstream.java:22-29`). Tests: `AwsTransportTest.lambdaInvocationIsSynchronousBoundedAndWireContractRoundTrips`, `ambiguousTransportFailureNeverRetriesOrFabricatesDecline`, `functionErrorsAndInvalidPayloadsRemainUnconfirmed`.

**Assessment.**

1. **The hop is IAM-only in fact, and weaker than the proposal's matrix says.** The template grants `lambda:InvokeFunction` from Processor to `Mastercard.Arn` and from Mastercard to `Issuer.Arn` as identity-policy statements (`infra/template.yaml:70-100`) with **no `AWS:SourceArn` / `aws:SourceAccount` condition and no resource-based policy**. Proposal S4 states the grant is "restricted by `AWS:SourceArn`" and that an unlisted principal is "denied by resource policy". Neither mechanism is present. In-account the expected deny still holds by absence of the grant, but the named control does not exist, and cross-account isolation (which a resource policy would provide) is not configured.
2. **No handler enforces application identity, by design.** `MastercardHandler` and `IssuerHandler` read the payload and act; `IssuerHandler` will persist issuer truth for any invoker, using a conditional put and rejecting a conflicting instruction (`IssuerHandler.java:18-31`). That matches D-G's choice (IAM-only, no token on the send path) and the proposal's §12 statement that SDK invocation carries no application TLS/OAuth identity. It also means the security of the seam is exactly the IAM grant — which is why the missing condition in (1) matters.
3. **The "current internal contract" is JSON, while the approved byte contract is unimplemented.** C2 specifies `POST /internal/sim-iso87a/v1/authorizations`, `application/octet-stream`, one 1–2048-byte body, and a same-profile 0110 response (`channel-contract.md:16`). The checkout implements that only as a pure decoder/encoder (`HttpApiV2RequestDecoder`, `HttpApiV2ResponseEncoder`, `C4HttpCarriageBridge`) with no handler and no route; the live contract is the synthetic JSON `SimulatedDecisionRequest`/`DownstreamReply` pair. The contract acknowledges the delta ("Current direct Lambda synthetic JSON transport is a delta to replace at this seam"), so this is consistent — but the proposal's S4 row should not be read as describing an already-approved wire contract at this seam.
4. **Adding OAuth to these hops would break the send path, as D-G says.** A token exchange before `sendDownstream` inserts an external dependency and a new failure mode between the durable `POSSIBLE_SEND` intent and the single downstream call (`AuthorizationService.dispatchCommitted`/`sendDownstream`). The current no-retry, unknown-on-ambiguity behaviour depends on that call being the only thing that happens after the intent commits. IAM-only is the compatible choice.

**Verdict: the proposal's D-G decision is compatible with the code and is the right one; the concrete gap is that the IAM grant is broader in *policy form* than the matrix claims (no `SourceArn` condition, no resource policy), and the S4 description should be corrected rather than copied into IaC.**

## 5. Contradictions with approved contracts and with atomic-journal admission rules

Five items, ordered by how much they constrain construction.

**CA-1 (MATERIAL) — S5 creates a public late-evidence route that the approved contract says does not exist.** `observation-contract.md:29` states "Late evidence uses same internal admission; no public late endpoint/automatic financial recovery", and C4 repeats "No public late-evidence endpoint/automatic FINANCIAL recovery worker or issuer-table fetch is commissioned". Proposal S5 realizes late admission as a **public authenticated mTLS REST route** under Option A (§6 S5, §7.2, §14 D-C). "Public authenticated" is honest about network exposure, but it is still a public route where the approved text says the internal P5 handler receives late delivery. `LateEvidenceAdmissionGateway`'s own javadoc encodes the approved rule and explicitly says "There is no HTTP route, no public endpoint, no notifier and no service/runtime wiring here" (`LateEvidenceAdmissionGateway.java:27-38`). This is the one place where the proposal, if implemented literally, would contradict a contract that owner decisions have not superseded. It needs an explicit contract amendment or a different realization (late admission stays on the internal invoke/VPC path; only normal C2 is externally exposed). It must not be settled silently in IaC.

**CA-2 (MATERIAL) — the proposal's C4 registry roles do not match the code's role model.** Proposal §5 defines `role ∈ {RELAY, ACL, PROCESSOR, NETWORK, RELAY_EVIDENCE, DIAGNOSTIC}`. The code has a four-value `C4PrincipalRole` (`ISSUER_SIM`, `PROCESSOR_AUTH`, `NETWORK_SIM`, `ACL_AUTH`) resolved by `C4KeyRegistry.resolve(environmentId, principal, keyId)` (`C4PrincipalRole.java:11-26`, `C4KeyRegistry.java:19-27`). Two problems: most proposal names have no counterpart and need an explicit mapping (`ACL→ACL_AUTH`, `PROCESSOR→PROCESSOR_AUTH`, `NETWORK→NETWORK_SIM`, relay countersignature is `NETWORK_SIM` per its javadoc), and **`DIAGNOSTIC` must not become a role**: diagnostic forwarding is deliberately a separate deny-by-default permission, `C4KeyRegistry.diagnosticForwardPermitted(env, principal, acquirerRef)`, which "does not confer a `C4PrincipalRole`, does not permit signing … and does not grant payment, receipt or durability authority". Tests pin the distinction: `C4LateDeliveryTest.wrongSenderWithoutDiagnosticPermissionFailsClosed`, `diagnosticForwardWithExplicitScopedPermissionIsAcceptedWithoutOutcomeAuthority`, `diagnosticForwardOutsideConfiguredScopeIsRefused`. Implementing §5's `role=DIAGNOSTIC` literally would hand a forwarder signing-adjacent standing that the code was built to withhold.

**CA-3 (MATERIAL) — the trusted transport context is too narrow for the certificate/client binding the proposal requires.** `C4AuthenticatedTransportContext` carries exactly `(environmentId, authenticatedSender)` (`C4AuthenticatedTransportContext.java:12-19`). Proposal §5 needs the leaf fingerprint, the token `client_id`, the registry version and the permitted context set at the final authorization point. Extending this record is a source change with a wide blast radius: it is the argument that gates `C4CarrierParser.bindSender`, `C4EvidenceVerifier`, `C4LateDeliveryVerifier` and every atomic evidence composer. The assessment does not propose the shape; it records that §5 cannot be implemented by configuration over this record.

**CA-4 (MATERIAL) — the proposal assumes atomic admission is live; the production wiring is on the legacy path.** `AwsRuntime.processor()` constructs `AuthorizationService` with the four-argument constructor (repository, `LambdaDownstream`, properties, clock) and installs none of the claim/dispatch-intent/result/network/late-evidence gateways (`AwsRuntime.java:34-42`). `DynamoClaimGateway` states in its own javadoc: "**Not activated in `AwsRuntime`.** … the production runtime stays on the legacy claim path until they are supplied" (`DynamoClaimGateway.java:25-31`). The atomic rules themselves are strict and must govern any new ingress: `authorizeAtomic` makes exactly one `claimGateway.claim` call and never falls back to `repository.claim()`; the send is permitted only when `dispatchIntentGateway.dispatchIntent` returns `COMMITTED` with `permitsSend()`; `REPLAY`/`RECOVERED` are knowledge and never a resend (`AuthorizationService.java:566-630`); `DynamoEventStore.append` composes event row + dedupe row + conditional HEAD + business rows in one `TransactWriteItems`, and a composed-business condition failure throws so no event exists without its transaction (`DynamoEventStore.java:88-142`). Consequence for this assessment: statements that "late evidence commits atomically with business and critical event" describe the **implemented but unwired** path. The proposal's access boundaries are compatible with it, but a compatibility claim cannot also imply the deployed behaviour is atomic today. Wiring is a prerequisite, not a property.

**CA-5 (MINOR, expected supersession) — C6/O4 still say `$connect` is IAM-signed.** `channel-contract.md:52` and `observation-contract.md:38` state the relay "IAM-signs `$connect`" and the handler validates the demo JWT "as well as IAM service context". Proposal §8 replaces that with a `$connect` Lambda authorizer validating a service **OAuth access token** plus the demo token, leaving IAM for callbacks only. Owner decision D-D adopts the OAuth-token form. So D-D is the current authority and there is no live conflict — but the contract text is now stale, and the Security review already carries an open advisory (`AD-01`) that pinned contracts must be overlaid explicitly. The delta should be authored through the normal contract-change/review path, not inferred by an implementer reading C6 alone.

Two smaller observations, recorded without severity:

- The proposal treats the "application re-validates the access token" as existing behaviour (§4.2). It is not (see §1 item 3). This is a completeness gap, not a contradiction, because C6 only promises that the upstream "retains existing JWT authorizer".
- `configuration-schema.md` is Terraform-shaped (backend, `use_lockfile`, variables, OIDC trust policy) but the checkout has **no `.tf` file and no `.github/` directory**; `infra/template.yaml` is SAM. The schema is therefore not a description of the existing IaC; adopting it means introducing a second IaC toolchain or translating it into SAM. The Security review already recorded "No .github/workflows directory was present … No Terraform/OIDC implementation is certified by the baseline SAM excerpt."

**Overall:** the proposal is coherent and internally honest, and it does not require weakening any protocol bound, idempotency rule or no-resend rule. It is not implementable by configuration. Two of its five areas need contract-level disposition before source work (CA-1, CA-5), and two need data-model decisions (CA-2, CA-3). Nothing here closes NV-01..NV-04 and nothing here is a Security verdict.

## 7. Source-level work the proposal implies (not authorized by this document)

Ordered so that each step is independently reviewable. None of this is started.

1. **Identity registry and authorizer.** Replace or supplement the native `TestJwt` authorizer on mTLS routes with a request authorizer that recomputes the leaf fingerprint, requires exactly one `ACTIVE` registry match, and compares token `client_id` to the certificate's client. Introduce the registry record (client id, env, status, cert fingerprints, allowed scopes/routes, permitted contexts, `c4KeyIds`, version) as a first-class type instead of overloading `AuthorizedContext`; keep `AuthorizedContext` as the resolved mandate so `AuthorizationService` is untouched.
2. **Transport context widening.** Extend `C4AuthenticatedTransportContext` (or add a sibling accepted by the verifiers) to carry `clientId`, `registryVersion` and the bound context, then update `C4CarrierParser.bindSender`, `C4EvidenceVerifier`, `C4LateDeliveryVerifier` and the composers in one reviewed change. Add negative tests for cert/token mismatch and cross-context access.
3. **Demo/service separation.** Add a second audience and the `X-Demo-JWT` header, enforce both at the edge and in the handler, and add the two deny tests that cannot exist today (service token on demo route, demo token on service route). Move console submission to the C1 route/body contract or amend C1 — do not leave a relay speaking `PurchaseRequest` at `POST /authorizations`.
