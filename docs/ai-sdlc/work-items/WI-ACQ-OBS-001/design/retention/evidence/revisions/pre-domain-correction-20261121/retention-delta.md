## 2. Classification and clocks

Every delta below is **SOURCED CLARIFICATION**, **PROPOSED NEW RULE**, or **UNRESOLVED CONFLICT**. “Sourced” means traceable to the recorded approved direction/contracts under D's overlay, not a claim of new review or approval. Existing detailed proposals (for example expiry transaction layout, cursor duration) keep their proposal status; citing them never upgrades them.

- **SOURCED CLARIFICATION — R-RET-01:** Functional history payload is usable only before original collectedAt + seven days; critical collectedAt is its original atomic business/event commit, best-effort collectedAt is first authorized collection (O8 line 77; D line 50; A line 21). occurredAt, later storage, callback, repair, read, reauthentication and duplicate delivery are not replacement clock origins. Use server-authorized collection metadata, not an arbitrary producer-supplied future timestamp.
- **PROPOSED NEW RULE — R-RET-02:** Make the endpoint explicit as a half-open interval [originalCollectedAt, originalCollectedAt + 604800 seconds), evaluated in UTC by the trusted reader/notifier/expiry service; at exact end, do not disclose payload. O8 specifies original-time expiry but not precision/rounding. Preserve original instant precision for logical checks; numeric epoch-seconds physical TTL must not make deletion eligible before logical end or the metadata barrier. Exact clock-skew tolerance for history is not specified and must not become an implicit extension.
- **SOURCED CLARIFICATION — R-RET-03:** Physical deletion may lag logical expiry; no access/callback authority follows from an expired item still being stored (A line 21; O8 line 78; official AWS TTL references). O8's <=48-hour purge target is explicitly proposed, not an AWS guarantee or approved deadline. Seven-day CloudWatch log retention (AWS line 28) is a separate store policy, not a journal TTL.
- **SOURCED CLARIFICATION — R-RET-04:** History read, duplicate, notification retry, quarantine, live reconnect and business read never renew an existing event's seven-day window (O7 lines 68–72; O8 lines 77–79). A genuinely new admitted business transition, including new verified late evidence, creates a distinct critical event with its own commit/collection origin (O3/O3a; P5); it does not resurrect or re-date the earlier events.
- **PROPOSED NEW RULE — R-RET-05:** Make no-renewal enforceable across all writers by keeping original collection origin immutable in event identity metadata, including after payload compaction. A fresh event ID cannot launder an old duplicate into new history. For a never-before-collected delayed best-effort observation, use first authorized collection as O8 states, preserve its earlier occurrence time/provenance, and do not claim timely execution or recovered completeness. Trust/allowable delay validation remains implementation/Security design, not a newly invented business age cap.

## 4. Expiry, Streams and no resurrection

- **SOURCED CLARIFICATION — R-RET-06:** O8 line 78 requires durable compact expired ranges, incremented expiryRevision and EXPIRED dedupe before/atomically with payload deletion. Native TTL cannot race ahead of that barrier. A proposed compliant order is: enforce logical expiry on every reader; persist marker/revision/dedupe conditionally against current identity; only then remove payload or enable its physical TTL. Do not arm an unguarded creation-time payload TTL that could delete before markers exist. An interrupted worker may leave expired payload physically present, never readable as retained history. Transaction layout/batch size are design proposals, not new approved business limits.
- **SOURCED CLARIFICATION — R-RET-06a:** O7 line 68 consumes event INSERT only and re-reads the exact source before fanout. TTL/service REMOVE, manual REMOVE and HEAD/dedupe updates do not become new events or financial actions. Delayed INSERT/repair pointer after expiry yields only safe resync/expiry metadata, no payload. Source absence without durable expiry explanation is SOURCE_INTEGRITY_GAP (O8 line 78), not fabricated successful coverage.
- **PROPOSED NEW RULE — R-RET-06b:** Guard duplicate writer/repair and expiry updates against the same immutable identity/collection origin and expiry status. Delivery after compaction cannot clear EXPIRED, decrement revision, reset lastSequence, restore an old payload or allocate a new ID merely to evade retention. A late physical TTL REMOVE for a former payload must not delete a different current metadata record or release bookkeeping twice. These are explicit race acceptance oracles derived from O6/O7/O8, not a prescribed database schema.
- **SOURCED CLARIFICATION — R-RET-06c:** A newly verified internal late result after old payload expiry is admitted through P5/C4 and D105–107, atomically updating evidence+business version+new critical event. Its own history window starts at that new commit. Prior expired history stays expired; prior uncertainty/evidence links remain internally explainable. No notifier, expiry worker, query, cursor refresh, reconnection, retry or newly empty history may execute authorization, reversal or inquiry (O3a31; O5a55; O7 69/71; AR R16/R20).
- **PROPOSED NEW RULE — R-RET-07:** Technical pointer/connection/control/cursor physical cleanup may occur only after its actual validity horizon is unconditionally closed, without removing the retained source or financial identity records. Delayed cleanup never extends authentication or cursor acceptance. No automatic seven-day grace period.
- **PROPOSED NEW RULE — R-RET-08:** If assertion replay prevention is adopted, reject reuse atomically across issuer instances and retain jti identity through the last permitted acceptance instant including configured skew. Do not refresh the original assertion's validity on repeat, do not conflate new jti with new payment identity, and do not use a cache-availability failure to bypass selected authentication. Security must validate the realized Keycloak behavior before this is treated as supplied evidence.
