## O1 — hook and durability classes
Every implemented/future capability requires the common hook AND versioned manifest before activation, including nonpayment auxiliary capabilities; no future operation is commissioned. A manifest declares tasks, conditional branches, producers, critical-transition budget, and durability class. Initial A includes receive, context-check, validate, idempotency-check, request-adapt, dispatch, response-adapt, business-persist, channel-response; network/issuer tasks only where observed.
CRITICAL_COMMITTED: event from committed business change, atomically durable with journal/evidence/head updates. Business claim, possible-send and verified result/late result are not inferred from tasks.
TASK_BEST_EFFORT: every task invokes started/terminal hook where observable; nonblocking per-invocation memory queue <=100 events/200KiB, asynchronous writer inserts directly into SAME event table. No separate history copy, no awaiting queue delivery before payment. Queue, invocation/crash and async Lambda retry limits can lose events. Missing preauth/start/terminal/producer observations remain explicit gaps; missing event is NOT FAILED. Proposed async writer within query/notifier responsibility, service-scoped async Invoke, maximum age1h/retries2 subject to runtime/IAM preflight. It cannot write business state or fabricate critical class.
TECHNICAL_SAMPLED: separate ADOT/OTel spans/metrics/safe logs asynchronously exported to configured AWS destinations. Sampling/drop/lifecycle/resource overhead remain; never proves task completeness or financial result. A received span cannot replace a lost functional event.
Preauth observations before business claim have no guaranteed durable transaction identity; use separate safe request metadata only where observed, never attach by guessed foreign correlation. Source redaction is mandatory: no raw ISO, attestation/signature, JWT, credentials, PAN/PIN/EMV/3DS blobs, arbitrary logs/error bodies in event table, ADOT or failure destinations. No zero-cost full per-task durability claim.

## O1a/O2a — immutable event identity and source ordering
Canonical payload (<=2048 ASCII/UTF-8 bytes) unchanged: schemaVersion,eventId,producerId,instanceId,actor,capability,version,manifestVersion,acquirerRef,merchantRef,terminalRef,transactionId,operationId,attemptId,correlationId,taskExecutionId,taskName,status,occurredAt,producerSequence,provenance,reason,parentTaskId,parentEventId,retryOfAttemptId,originalOperationId,startedAt,endedAt,elapsedMicros,clockQuality,evidenceRef,gapCode. Optional absent fields normalize null for RFC8785 content hash. Bounds/enums remain prior event contract: IDs1–64, context refs1–128, capability/version/manifest1–32; UTC RFC3339 times, nonnegative sequence/duration, manifest task/reason, actor CHANNEL/ACL/PROCESSOR/NETWORK/ISSUER, status STARTED/SUCCEEDED/FAILED/SKIPPED, provenance OBSERVED/INFERRED. Reject undeclared payload fields.
Dedupe identity=(environment-bound producerId,eventId), stable producer namespace across boots; durable critical ID allocation from original transition token, original instanceId retained on redelivery. Same canonical hash no-op; changed immutable content quarantined as integrity conflict. Validate service producer and business context BEFORE dedupe. Collector must not silently reassign context. Task class cannot assert critical journal metadata.
Source wrapper, not canonical content: deliveryClass, eventSha256, journalVersion (critical only), committedAt (critical only), collectedAt, sourceSequence, storedAt, stateAfter (critical-only journal state at that committed version; null for tasks, never caller-selected/current authority). For critical events collectedAt=committedAt; best-effort first authorized collection is retained across redelivery. occurredAt is producer time, not causal proof. No cross-clock duration claim.
Event table keys proposed:
- PK ENV#<environment>#ACQ#<acq>#MID#<merchant>#TX#<transaction>, SK E#<12-digit sourceSequence>, immutable payload stored ONCE.
- SK HEAD in same partition: lastSequence, firstRetainedSequence, expiryRevision, latestKnownBusinessVersion reference, last collection time.
- global-in-environment producer/eventId dedupe metadata partition: payload hash + original context/source key/sequence, no second payload. Retain required identity metadata while business links remain; after payload expiry mark EXPIRED, never recreate expired payload on redelivery.
- optional list index keys acq+mid / firstReceipt+transactionId; it is eventually consistent and not proof of exhaustive catch-up.
Every append conditionally increments HEAD and inserts event+dedupe metadata atomically. Critical append includes business version/head/evidence in SAME DynamoDB TransactWriteItems account/region. Best-effort append uses event-table transaction only, retries storage/version contention without invoking payment. Concurrent task/critical appends serialize by HEAD CAS; deterministic tokens handle ambiguous writes. No allocated sequence hole from failed append. Immutable sourceSequence is COMMIT order, not cross-producer execution order; critical business versions and causal links remain separate.
Streams can reorder records from different items. Notifier/browser must never substitute stream arrival order for sourceSequence. Delivery exact replay never allocates new sequence. Source sequence gaps mean not-yet-fetched/lost delivery/expiry or integrity issue; absence of best-effort task emissions can exist without a source sequence gap and is detected against manifest.

## O3 — atomic DynamoDB business + queryable event, no dual write
Before send, one transaction creates/updates mandatory business record, idempotency generation/head, critical event itself, event HEAD/dedupe and slot accounting. No business-write-then-event-write; no PostgreSQL/DynamoDB dual write; no second event payload copied for history or notification. A failed transaction changes neither business state nor critical event. Ambiguous commit -> strongly consistent lookup of stable transition token/business/event before any send; inability to establish state means UNAVAILABLE, not proof of no-send.
CLAIMED_NOT_SENT may progress only in its ORIGINAL running invocation through atomic POSSIBLE_SEND+critical event before invoking downstream once. Event-store failure on this required atomic write is business-admission failure, not async backend failure. Retry/restart of old claim NEVER resumes sending; future notification workers cannot perform the financial CAS. A crash after POSSIBLE_SEND before actual invocation is deliberately possible-send uncertainty.
P5/C4 authenticated, correlated verified issuer evidence becomes processor-known only when evidence+business version+critical consultable event commit atomically. Late evidence uses same internal admission; no public late endpoint/automatic financial recovery. Event/history/task/span alone cannot admit payment result.
HTTP payment result uses readable journal (or committed version read in current invocation), not event-table history as fresh financial authority. A signed but uncommitted reply, issuer-only table read or disconnected green UI is not confirmation.
Notifier/ADOT/management callback/connection table outage by itself does not block payment. Async intermediate writer outage loses or delays tasks, not payment. Required business+critical event transaction outage before send prevents send; after possible send current invocation returns conservative NOT_CONFIRMED unless prior committed result readable, unreadable restart UNAVAILABLE. No auto payment resend, rollback, reversal or inquiry. Existing key, prior precedence and24h generation rules unchanged.

## O4 — no console accounts: proposed narrow demo/service boundary
No console users, login screen, registration, password, roles, user-to-context registry or per-person authorization is introduced. Technical connection/subscription state is routing, NOT an account. Acquirer/merchant/terminal are business mandate data, NOT authenticated human identities.
Existing AWS /authorizations JWT and service IAM/principal/subject-to-context controls remain. Do not strip authorizers, expose credentials in HTML, or claim anonymous public access approved. PROPOSED initial demo: presenter-operated single isolated synthetic environment; HTML plus same-origin HTTP/WebSocket relay bound ONLY to127.0.0.1 on presenter's machine, viewed locally or screen-shared to client. Not direct public Internet or remote-client-device hosting. No stack/tool/runtime selected by this specification.
Relay holds short-lived existing-service JWT on server side for upstream HTTP operations, a dedicated service principal provisioned only for demo fixtures; no human console account. Existing server subject-to-business-context registry may register DEMO-SERVICE for fixed synthetic contexts, not a human user registry. Actual noninteractive token acquisition/provider compatibility must be preflighted; if unavailable, service requests fail closed, never bypass current JWT. AWS service IAM signs relay upstream WebSocket $connect and authorizes query/notifier callbacks; implementation must verify actual API/authorizer support. No issuer-table access through console; diagnostics remain offline/internal operator tools, not a console role or endpoint.
Relay enforces exact loopback Host and Origin, same-origin JSON POST/read and WebSocket upgrade, rejects wildcard CORS/cross-site traffic and DNS-rebinding hosts; binds fixed environment/context allowlist at startup. No browser override of identity/env/service policy. All people sharing this demo have same allowlisted synthetic business visibility, not private per-user accounts. Existing merchant/acquirer eligibility still checked on submit; subscription/query context must lie in fixed demo scope. No public/external environment or live credentials allowed by this proposal.
Service principal revocation/environment stop closes connections and denies subsequent operations; there is no human role revocation flow. Presenter shutdown clears relay memory. Token secrecy/lifetime, local threat boundary, Origin enforcement, SigV4/JWT and Java25/ADOT compatibility require independent Security/architecture preflight. A remote/public anonymous demo would be a DIFFERENT owner decision, not silently inferred.

## O5 — technical connections and subscriptions (PROPOSED limits)
API Gateway owns WebSocket transport; technical connection table stores connectionId, authenticated SERVICE binding/environment/demo allowlist revision, createdAt/lease expiry and subscriptions. No username/password/person role fields. Origin controls at loopback relay do not replace upstream service authentication. Only trusted $connect context establishes service binding; bodies cannot claim it. Revalidate service/environment scope on subscribe/query/notification; missing or revoked binding fails closed. Service IAM permissions and routing metadata never imply a browser user account.
Proposed max50 active upstream connections/environment, max10 transaction subscriptions/connection, technical lease30min refreshed by heartbeat/valid activity; expired/gone connections cleaned even if $disconnect is missed. Callback410 deletes stale routing state; callback success means Gateway accepted, NOT browser received or durable acknowledgement. $disconnect cleanup is best effort; never wait for it on payment path.
subscribe message: version1,action=subscribe,requestId,subscriptionId (client random1–64),environmentId,context{acquirerRef,merchantRef},transactionId. No global wildcard/issuer subscriptions initially. Handler persists routing subscription BEFORE reading strong source HEAD. Ack: action=subscribed,subscriptionId,generation (server-generated per install),headSequence,expiryRevision,firstRetainedSequence. Client buffers matching live frames from request time, even BEFORE ack. Duplicate subscribe token returns same active generation; context change/new connection requires fresh generation; discard frames from former generation.
New transaction flow: establish transport first; generic UI may await transactionId from POST then subscribe to that transaction and catch up from0. Do not fabricate a future transaction ID or claim subscription means payment submission. Never auto POST on connect/reconnect. This closes events-before-transaction-subscribe race via source catch-up.

## O6 — subscribe-before-catch-up and query cursor protocol
After subscribed ack, GET /console/v1/transactions/{id}/events?snapshot=new&after=<lastSourceSequence>. Service resolves fixed environment/business context. Strongly read HEAD for snapshot H >= acknowledged head, capture expiryRevision R and first retained sequence F, then strongly consistent base-table Query after cursor up to H (not GSI). Response: version1,transactionId,snapshotHead=H,expiryRevision=R,firstRetainedSequence=F,events (source wrappers+canonical payload),coveredThrough,expiredRanges,gapRanges,nextCursor,completeThroughSnapshot,retentionTruncated. Keys/cursors are opaque to browser.
Default/max page100 events or256KiB, combined catch-up max1000 events or1MiB per reconnect pass. Signed opaque cursor binds demo service scope/environment/context/transaction/subscription generation/H/R/last sequence, max15min. Cursor integrity does NOT authenticate a user; relay/service remains authority. Unknown/tampered400; invalid scope403; expired cursor or changed expiry revision/generation410 RESYNC_REQUIRED; return safe range metadata and new snapshot instruction, never silently reset cursor to newest.
Snapshot pagination has fixed H; events appended after H are buffered live then merged. Deduplicate producer/eventId+hash and sourceSequence; same ID/sequence different content -> explicit integrity gap, do not overwrite. Emit contiguous source order; receiving sequence N+1 with N missing triggers source catch-up, not fabricated event. Page overlap/repeated delivery no duplicate task/business transition. completeThroughSnapshot means every sequence in requested range is represented by event or explicit expired range, no unexplained gap; not every manifest task observed or financial finality.
If backlog exceeds1000/1MiB: action/status RESYNC_REQUIRED with continuation/paged snapshot and visible lag; no unbounded in-memory queue. Browser live buffer max1000 events/1MiB, on overflow mark partial, discard nonessential buffered frames, establish new snapshot; source fetch restores RETAINED events. Do not claim lost/expired/unwritten tasks recovered. Query under concurrent logical expiry returns410/new retention metadata rather than stale complete assertion.
Live frame: version1,action=event,subscriptionId,generation,transactionId,sourceSequence,eventId,producerId,eventSha256,record (<=2048 payload plus allowlisted wrapper),authority=RECORDED_EVENT. Frame<=4096 bytes, no raw journal/proof. A frame approval is a recorded journal-version observation, not new issuer evidence; authoritative current outcome comes from HTTP business response/journal-qualified detail.
Subscribe BEFORE catch-up is mandatory; delivery is at-least-once when retried, not exactly-once or guaranteed to every connected browser. After snapshot merge, buffer records >H; if callback was silently lost and no new event arrives, browser sends WebSocket sync/heartbeat every30s (not one-second HTTP polling) and server returns strong head/F/R for its bounded subscriptions. New head beyond last covered source sequence triggers HTTP catch-up. Lack of heartbeat response marks connection UNKNOWN/DISCONNECTED and reconnect with jitter1/2/5/10/30s. A heartbeat cannot prove completeness after its asOf.
Initial/history/reconnect, detected gaps and explicit refresh use HTTP queries SAME event table. No every-second event polling fallback. WebSocket down => UI shows disconnected and retained history can be explicitly loaded; payment control never automatic retry.

## O7 — Streams, bounded notification retry and replay beyond24h
Streams retention24h is notification transport window, not retained-history source. Notifier consumes INSERT of event rows only, ignores HEAD/dedupe/capacity/technical updates. Validate producer/hash/context/version and event class; critical requires committed source/journal-version reference, best-effort cannot masquerade as critical. No second persisted history projection. Notifier reads exact source row before fanout; stale/deleted/expired source means no payload push, safe expiry/resync metadata only.
Notifier selects matching CURRENT technical subscriptions, callback retries transient failure with partial-batch/bisect controls (proposed max5 stream retries/max age1h). Idempotent callback may repeat same event, browser dedup mandatory. Retry notification NEVER invokes authorization/evidence handler or updates payment result. No per-browser pending delivery queue or durable acknowledgement ledger. Disconnected browser is not reason to retain events forever or backpressure payments; retain only source-policy window. Callback410 removes connection; no route => no enqueue for offline browser.
Mutable notification metadata on source row (outside event hash) may track attempt time/nextAttempt/attempt count/fanoutAttempted; this is NOT payment state/delivery guarantee and contains no second payload. No raw failure-destination event export; sanitized source pointer/reason only. Deterministic poison (schema/hash/context) isolated/quarantined as metadata with visible source gap; original retained until normal expiry, never silently labeled delivered. Failure to store alert/quarantine cannot delete source or change journal.
After >24h outage, reconnect catch-up still queries retained source directly. Proposed notifier repair scans bounded pending source-pointer index max100/page,1000/run, every5min, overlaps/reconciles against source metadata; eventually consistent index absence is not proof of delivery. Repair fanout only to currently connected matching generations, not offline backlog; no FINANCIAL privileges. A source event marked fanoutAttempted need not have reached all browsers; heartbeat/head catch-up—not marker—is recovery authority. A late callback for old generation is ignored. Expired source returns truncation, not fresh resurrection.
No additional duplicate event/history materialization in replay, dead-letter or failure store. Quarantine pointer and source identity metadata may persist under proposed retention, never contain payload copy. Exact worker scheduling/destination/IAM remains D3 proposal.

These metadata and business storage costs require architecture/cost review separately. Technical connection metadata lease expiry never deletes events or business records.
