## C1 — HTML JSON ingress
POST /console/v1/authorizations, HTTPS, application/json, UTF-8 restricted to ASCII values, body <=4096 bytes. One preprovisioned demo user signs in through existing issuer; no multiuser console administration. Proposed local relay holds short-lived demo-user JWT, upstream verifies issuer/audience/signature/expiry and existing subject-to-context registry. Service IAM remains separate; O4 and C6/C7 bind service/demo scope. No caller identity, decision, route, generation, actor, fault or arbitrary ISO input in browser body. Reject duplicate/unknown JSON keys, nulls, floats, coercion and non-ASCII references. Exactly these required fields:
contractVersion="1", operation="A", correlationId (1–64 profile alphabet), acquirerRef/merchantRef/terminalRef/paymentRef (1–128 profile alphabet), credentialFixtureRef (1–64), amount (string matching [0-9]{1,4}\.[0-9]{2}, value 1.00–9999.99), currency="USD", entryMode="simulated-contact" or "simulated-contactless", cvm="simulated-verified" or "simulated-not-required", cryptogramPresent (boolean).
Optional risk="pass" or "reject" (default pass), priorAuthorizationId (1–64).
No leading zero amount except zero itself, which fails domain minimum. Minor-unit conversion exact, no rounding. POS channel fixed by endpoint. Apply P3a order: current context/schema, authorized prior/key lookup, pinned replay comparison, current fixture/route resolution only for new work. Request DE48 admission maximum 826 reserves the complete 173-byte response suffix; structural maximum remains 999. Reference validation precedes replay.
ACL assigns authorizationId/transactionId/attemptId/generation, durably stores exact wire instruction identity and aliases, then adapts request and validates response per P1–P6 including P2a/P3a/P5 and channel C3/C4. 051/071 and VERIFIED/NOT_REQUIRED are synthetic representations, not actual EMV claims.

Response schema, dispositions, status and failure precedence are defined ONCE in C3 below; no independent status default overrides it. No credentials, raw ISO, attestation, signature, private result extension or issuer table details appear in channel output. Context-authorized console detail exposes sanitized processor evidence only; there is NO console issuer diagnostics route; issuer-only diagnostics remain separate internal operator/test tools.

## C2 — private simulator byte boundary
ACL → simulator POST /internal/sim-iso87a/v1/authorizations over authenticated HTTPS, not public browser route. application/octet-stream, X-Simulator-Profile: SIM-ISO87A-v1; one complete body 1–2048 bytes, exact Content-Length after transport decoding. No compression, chunk semantics exposed to parser, newline framing or text/base64 on the logical interface. Responses HTTP 200 same profile/media type and exactly one 0110 <=2048 bytes. HTTP status is transport, never DE39.
Use API Gateway HTTP API payload v2 adapter if chosen: octet stream decoded from event body only when isBase64Encoded=true; reject invalid/noncanonical base64 or decoded size >2048; response body base64 with isBase64Encoded=true and octet-stream. Gateway wrapper is not ISO framing; public callers cannot submit wrapper flags as application data. Current direct Lambda synthetic JSON transport is a delta to replace at this seam, not already ISO-enabled.
Require authenticated service principal with route-specific permission and server context/fixture resolution; no trust in X headers for identity. Mutual TLS or IAM-controlled ingress realization remains human architecture/Security gate; candidate recommendation uses private API Gateway IAM-authorized HTTPS with SigV4 service identity. No new public function URL. Maximum Lambda/API envelope size comfortably exceeds 2048-byte decoded body.
Deadline 2 seconds from processor dispatch, inherited AWS A default; no automatic retries and no assumed harvesting of timed-out invocation. Empty/missing body/timeout/non-200/invalid 0110 after possible dispatch => unknown absent previously confirmed evidence. Authenticated explicit non-forwarding P4 rejection is different. Wrong media/profile or invalid bytes before simulator admission => safe HTTP 400/415, no issuer dispatch; ACL still cannot infer payment non-delivery from an untrusted transport error.
Normal and late evidence use the exact P5 internal attestation/admission handler; no public financial reconciliation endpoint or automatic financial worker commissioned.

## C3 — comprehensive channel response and precedence (D2 amended policy; PROPOSED D3 detail)
Every JSON response <=4096 UTF-8 bytes has exactly these keys: contractVersion="1"; authorizationId, transactionId, attemptId, correlationId, originalCorrelationId (strings under profile bounds or null); outcome (APPROVED/DECLINED/PROCESSOR_REJECTED/NOT_CONFIRMED or null); disposition (COMPLETED/PENDING/REPLAY/REJECTED/NOT_DISPATCHED/UNAVAILABLE); businessVersion (positive committed integer or null); asOf (UTC RFC3339 time this response's knowledge was evaluated); observation (COMPLETE/PARTIAL/UNKNOWN); serverFreshness (CURRENT/STALE/UNKNOWN); error (null or enumerated code below). No unknown keys. attemptId identifies this admitted channel attempt when known; never fabricate an authorization ID before claim. Current invocation may retain IDs assigned/observed independently even when storage becomes unavailable. Unreadable restart/history returns no unverified original ID/version/outcome. Caller-requested correlation may be echoed, not treated as trusted original correlation. Access denials disclose none of the stored original IDs. Client connection state is local, not a response field.

Apply this precedence top-to-bottom; O3/O3a describe mechanics, this table determines observable HTTP/JSON. First establish current authorization; then use readable durable evidence before degrading to current-invocation observations; no cached client outcome is server evidence.

A pre-dispatch explicit PROCESSOR_REJECTED business result committed under P4/P5 has precedence as readable durable evidence; validation failures before business admission use null/REJECTED, not an invented payment decision. Notification/query-adapter/telemetry-only outage cannot replace a readable committed business result with UNKNOWN or prevent initial send. Telemetry-only outage need not set payment error; no inference about task completeness from sampled span availability. Notification/WebSocket/query-adapter/ADOT outages alone never reject business admission: business journal+critical consultable event commit atomically, then proceed without awaiting any async backend. If a confirmation was read durably in this same invocation before a later store outage, retain that known committed version/asOf and 200 result, marking serverFreshness UNKNOWN and observation PARTIAL/UNKNOWN; later unreadable restart cannot reuse that memory. Missing body/HTTP timeout is not evidence of no-send. No Retry-After, automatic POST retry, redispatch or rollback. GET/refresh/reconnect never initiates processing. UI may show an earlier client snapshot only separately marked 'last observed', with its original asOf/version and stale/unknown indicator; never copy it into a new authoritative server response. ## C4 — bounded signed evidence carriage (PROPOSED architecture, not D1 construction approval)
Keep C2 body EXACTLY one octet-stream 0110 <=2048 bytes; do not append metadata to the body or put it into DE48. Every normal 200 response additionally carries exactly one X-Simulator-Evidence header: standard RFC4648 padded base64 of canonical RFC8785 JSON envelope <=4096 decoded bytes (<=5464 encoded characters). No duplicate/folded header, compression, whitespace in base64, or unknown envelope keys. Total response headers <=8192 bytes; deployment must verify API Gateway limits and body/header preservation before use. Do not log this header/body or expose to browser, traces or CORS.
Envelope exact keys: version=1, mode=DIRECT or RELAY, attestation (P5 signed bound fields including added responseSha256), keyId (1–64 profile alphabet), signature (canonical standard base64 of exactly 64 Ed25519 signature bytes), relay (null or object below). Signature covers canonical attestation JSON bytes, NOT an oracle flag. P5's signingPrincipal/keyId are inside signed attestation; outer keyId must match signed keyId and configured principal key. responseSha256 is lowercase 64 hex SHA256 of the EXACT received decoded octet-stream body (before ISO parsing, after HTTP transport decoding), with no reserialization. instructionSha256 binds the original 0100. Both hashes and complete P5 domain fields must match. This avoids any circular processor-receipt lookup: sidecar brings the proof for first admission.
DIRECT: authenticated transport sender must equal configured attestingPrincipal=attestation.signingPrincipal, with permitted P4 role/mandate. RELAY: authenticated sender must be NETWORK-SIM; inner issuer attestation/signature/keyId remains unchanged. relay exact object: principal=NETWORK-SIM, receiptId (1–64), deliveredAt (UTC RFC3339), keyId (1–64), responseSha256, attestationSha256 (SHA256 of canonical inner attestation), signature (base64 64 bytes). Relay signature covers canonical relay object excluding signature; binds issuer content hash, exact response hash and relay receipt/time; role/key/mandate must match authenticated sender. Network cannot replace issuer signature with network signature. Duplicate/conflicting evidence handling remains P5. Sender identity comes from authenticated service transport context, NEVER an X header/body assertion. TLS principal binding/IAM mapping, key custody/rotation and Ed25519 implementation await architecture/Security approval.
Late delivery: authorized internal P5 handler receives canonical JSON envelope <=8192 bytes with exact keys version=1, responseBodyBase64 (standard canonical base64 of original <=2048 response bytes), evidence (same <=4096 C4 envelope), deliveryReceiptId (1–64). The authenticated late sender must be the DIRECT signer or authorized RELAY principal; a diagnostic delivery principal may only forward unchanged signed proof under explicit scoped delivery permission. Delivery ID alone grants no decision authority. Verify body/envelope bounds and canonical encodings, sender/role/key/signatures and both hashes, then P6 ISO/binding checks, then atomic P5 business evidence+receipt/version+critical consultable event commit, then channel result, then asynchronous notification/ADOT export. No public late-evidence endpoint/automatic FINANCIAL recovery worker or issuer-table fetch is commissioned; notifier repair is observation-only.
Missing/oversized/unavailable/mismatched header, absent key/signature, unknown key, bad signature/hash/sender/relay, or unresolvable supplied attestation => reject candidate evidence before business admission, sanitized error only. After possible send retain UNKNOWN unless a readable committed confirmation exists; do not infer non-delivery, retrieve a nonexistent receipt as proof, or retry authorization. A producer unable to supply attestation returns a transport failure rather than an unsigned confirming 0110; late authentic delivery may reconcile later via same handler. Wire example artifacts supply exact body/header/envelope bytes; signature material there is explicitly noncryptographic interface-shape fixture data, while future deployed carrier MUST contain actual verifiable signatures. No VALID flag is accepted on this interface.
