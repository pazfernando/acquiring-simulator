## 6. Item 2 — The single-credential WebSocket handshake

**Verdict: conditionally acceptable (no new IMPORTANT defect), with the revocation path and log hygiene as carried, still-open conditions, and one new ADVISORY (ADV-2, an ambiguity in the carried client table that qualifies the "single credential" claim; see §6.5).**

### 6.1 What the removal of the second identity actually costs

The old design had the relay IAM-sign `$connect` and carry `X-Demo-JWT`: a service identity that gated connection establishment and a user identity that bound the socket to the demo subject. With the relay gone, `$connect` sees one bearer credential. What is genuinely lost is (i) transport/establishment gating by a service identity the browser could never hold, and (ii) a two-factor separation between "something authorized to speak at the edge" and "the demo subject". What is **not** lost: the socket was already bearer-token dependent (the demo JWT was always required and always validated by the `$connect` handler), the boundary is already accepted as non-mTLS by owner decision D-D, and the socket's authority was always observation-only (`ws.observe`), never financial. The delta therefore trades defense in depth for architectural coherence — a browser cannot hold a service secret (owner K-3 constraint, correctly treated as a constraint, not a preference), and the alternatives (one-time ticket, cookie session, cloud BFF) each reintroduce either a new authenticated endpoint or a relay under another name, which rev4 §3.2 correctly identifies. The rev2 review already warned that "forged valid service+demo tokens are enough absent additional binding" on the non-mTLS socket; the delta makes the honest equivalent statement: one stolen token is now enough, until expiry or revocation.

### 6.2bis A qualification the design body carries but does not reconcile: `svc-console-ws`

rev4 §7.3 still lists `svc-console-ws` with scope `ws.observe` at the WS audience, while S6 and §3 describe the socket as carrying exactly one credential — the demo token (`sub` = demo subject, scope `ws.observe`). If a service token from `svc-console-ws` remains acceptable at the `$connect` authorizer (same audience, same scope), then the WS endpoint in fact still accepts a second credential class whose holder is not the demo subject, and rev4 §1.1's "one identity (demo)" and §3.3's identity-count statement are over-broad. This may be a deliberate leftover (the client exists "if it ever mints observation tokens"), but a formally stated one-credential boundary must either retire `svc-console-ws` or name exactly which of its tokens, if any, the authorizer accepts and how that is distinguishable (e.g., a distinct scope plus subject-of-system assertion). This is ADV-2 in §12; it does not by itself invalidate the single-credential design because the client is described as latent, but it must be resolved by the Requirements delta rather than left implicit. (In reading this, note the separate question it does not raise: the demo token's `sub` check stays mandatory either way.)

### 6.2 The compensating control set, judged control by control

- **Token in `Sec-WebSocket-Protocol` (option A).** The stated reason (browsers cannot set custom headers on `new WebSocket()`) is correct and the subprotocol is the standard browser-native carrier for this constraint. It is a real reduction versus the query string (option B): the token never appears in a URL, so no browser-history/proxy-log/Referrer exposure. Judged adequate **as a design**, with two conditions the design itself names and this review endorses: (i) the token must be excluded from every access-log configuration — CloudFront logs, API Gateway execution/access logs, and any WAF sampling — because handshake headers otherwise persist the bearer credential at rest in observability stores; the design's explicit fallback to option B if log hygiene cannot be proven on the chosen stack is a good, verifiable escape hatch; (ii) the token must be short-lived (≤900 s) and narrowly scoped (`ws.observe`), which is specified. Residual: a JWT in a subprotocol header is still a bearer credential visible in any TLS-terminated hop's capture; `wss://` limits this to intended terminators. Acceptable residual.
- **Exact `Origin` validation.** Genuine but secondary. The `Origin` header is browser-controlled (non-browser clients can forge it), so it is not an authentication control — the token is. Its real value: (a) it defeats cross-site WebSocket establishment from attacker-controlled pages, which matters because WebSocket handshakes are *not* subject to CORS and a page on any origin could otherwise complete a handshake using credentials the browser happens to have (none here — token is explicit — but exact Origin also prevents confused reuse of session-adjacent state); (b) it constrains which page context may pair with the WS endpoint, closing standard-config-mistake paths. Correctly required in addition to the token, not instead of it. The design honestly separates the two (S6 row in the matrix).
- **Per-frame revalidation.** Correctly carried from rev3 §5. This remains the weak link **because it is not built**: rev3 §5.4 (and the rev2 review's Q4) established that registry revocation needs status/version fields, a WS revalidation path, and a scheduler for idle connections; none are implemented, and rev4 makes no claim that they are. "Closed ≤1 heartbeat" is a requirement, not a delivered property. OPEN by carry-forward, unchanged in strength.
- **900 s lease.** `min(jwtExp, connectTime + 900 s)` = `jwtExp` for 900 s demo tokens; consistent, and the lease number in the pinned contract (30 min) is superseded via the D-1/D-5 delta rather than silently. With one credential, lease expiry is the only *guaranteed* upper bound on compromise impact — this raises, not lowers, the weight of the lease, and the design keeps it.

### 6.3 Is the set sufficient? Residual named

Sufficient **as a design** for an observation-only, non-mTLS, owner-accepted boundary, provided all of: (1) registry revocation fields/scheduler are actually implemented and fail closed (carried OPEN, NV-03); (2) subprotocol log hygiene is proven or the ticket fallback is taken (design condition); (3) `Origin` is exact-matched, not suffix-matched; (4) the edge rate limits (S6: ≤6 connects/min/subject, reserved authorizer concurrency) are implemented as specified. Residual, restated not waived: a stolen demo token can observe the demo context's synthetic history stream until token expiry/revocation from anywhere on the Internet with no client certificate — the direct consequence of one-credential carriage plus P-1's public reachability, already the accepted consequence of D-D and P-1 for the HTTP path and now extended to the WS path. The single-credential socket is **acceptable**; it must not be treated as covered by D-D's text (rev4 §3.3 says exactly this, and this review concurs with the flagging).

## 7. Item 3 — The public console surface

**Verdict: coherent and honest as a design; two ADVISORY gaps (ADV-1, ADV-3); one new ADVISORY on browser-flow hardening details (ADV-6).**

### 7.1 Same-origin plus no CORS — genuine control or convenience?

**Both, and the design should be understood as: no-CORS is a *supplementary* browser-side control; the *primary* control is "no ambient credentials".** With SPA and `/api/*` on one hostname and no CORS configuration at all (not even a wildcard), a cross-origin browser context cannot read responses (Same-Origin Policy) and cannot complete preflighted requests (the API's requests always carry `Authorization`, which makes them non-simple and preflight-gated; the preflight gets no `Access-Control-Allow-Origin` and fails). Cross-origin "simple" requests (e.g., a JSON body sent as `text/plain`) can still be *sent* by an attacker page — no-CORS does not prevent that — but they carry no token, are rejected 401, and the attacker cannot read the response. What makes this safe in practice is that every call carries an explicit header and there is no cookie at the API: rev4 §2.5's "Nothing is ambient" row is the load-bearing control and is stated correctly. The WebSocket `Origin` check supplies the analogous control for the socket (§6.2). So: genuine, but the review's caution is that same-origin/no-CORS is routinely over-credited; here the design does not over-credit it — it correctly pairs it with the ambient-credential absence. One measurable retest for later: exact negative tests — cross-origin preflight failure, `text/plain`-type forged POST rejection, and absence of any `Access-Control-Allow-*` response header on every route.

### 7.2 Demo token storage and renewal

In-memory access token only; no `localStorage`/`sessionStorage`/cookie/URL fragment; memory-only refresh token with rotation, 8 h absolute session cap (proposal), revoked on logout; re-login as the alternative. This is the strongest practical posture available to a public SPA: XSS can still read JS memory, but nothing survives page reload in attacker-readable storage, and the SSO cookie at `auth.<domain>` is correctly characterized as an issuer convenience the console never reads. Reasonable. See ADV-6 for the hardening details not yet specified.

### 7.3 XSS blast radius

Named correctly in rev4 §2.6 as the highest-impact browser risk. Judged concretely: an XSS in the SPA yields the access token (≤900 s) **and** the refresh token (up to the absolute session cap) — i.e., session takeover with read of synthetic history and initiation of synthetic payments until expiry/rotation/revocation. It does **not** yield: any service secret (none exists in the browser by construction, with a CI build-time scanner as a guard band), any C4 key, any mTLS identity, or the issuer database. CSP `default-src 'self'`, `script-src 'self'` with no `unsafe-inline`, no third-party script, `connect-src` allowlist, `frame-ancestors 'none'` and `no-referrer` is a strong, conventional mitigation set. Bounded, and the bound is honestly stated. ADV-6 adds rotation-detection and flow details below.

### 7.4 The issuer login page as the primary credential-stuffing target

**Yes — and this is the analysis the design calls out correctly** ("the login page and token endpoint are internet-reachable and are now the primary credential-stuffing target"). Proposed bounds: WAF rate rule 20 req/5 min/IP on the OIDC paths plus Keycloak brute-force detection with failure-factor and temporary lockout; alarms on login failures per IP/subject. Adequate as a *bound*, not as an elimination. Residuals, restated: (i) per-IP rate limits are trivially diluted by distributed sources; the per-account brute-force lockout is the only subject-scoped bound, and with a single demo user, lockout also becomes a denial lever against the legitimate demo (an inherent tension P-1 accepted in kind); (ii) with one demo principal, any successful guess = full console access including payment initiation (§8 below); (iii) rate-limit values are proposals, unexercised. Protection: adequate-for-design with named residual; no claim of adequacy against a distributed attacker is made by the design, and none should be.

### 7.5 Edge claims

CloudFront + private S3 via OAC (no website endpoint), ACM TLS 1.2+, managed WAF rule groups, Shield Standard with an explicit "no claim of DDoS immunity" — proportionate and honestly framed. All values (rates, throttles) are proposals; none was exercised.

## 8. Item 4 — Blast radius of a compromised demo token

**Verdict: yes, compromise yields both read of synthetic history and initiation of synthetic payments; the design states this plainly (§2.6 first residual row) and the bounding controls are real but finite.**

Abuse path and impact, judged against the design: a stolen demo JWT (phished, XSS-read, or gathered by guessing the demo login via the public issuer) presented to the public API authorizer passes `aud`/`scope`/subject checks because the attacker is indistinguishable from the legitimate demo user — P-1 accepted exactly this. With it, the attacker gets console reads for the single shared demo context and can initiate synthetic authorizations within the fixed synthetic mandate, subject to: channel validation (C1 bounds, amount ≤ 9999.99, fixed USD, synthetic fixtures), idempotency generation rules (no unintended second authorization), rate limits (proposed 100 req/5 min/IP and 5 rps throttle), token expiry (≤900 s or absolute session cap if refresh is also stolen), and registry/revocation controls where realized. **Bounding controls that do exist:** audience separation is a genuine limiter — the demo token is rejected at the service hops (S2: "demo token replayed here → 403"; the console→ACL hop requires mTLS plus an `svc-console` service token), so compromise of the demo credential cannot move money-style calls into the ACL/processor path with service identity; and `ws.observe` confines the socket to observation. **Bounding controls that do not exist:** there is no per-session or per-context synthetic payment volume/quota beyond generic rate limits, and no alert specifically on anomalous payment-initiation rates by subject (only generic 4xx/429 alarms are proposed — cost/abuse monitoring is WAF-centric). For a simulator with a single demo mandate that is proportionate, but it should be recorded as residual: the blast radius is "everything the demo user can do, at the demo's rate limits, until expiry/revocation". Restated, not waived — this is P-1's accepted consequence.

## 9. Item 5 — Disposable Keycloak (rebuild-not-repair)

**Verdict: the model is coherent and internally honest, the gap it leaves is real but is exactly the gap K-1/K-2 accept; no secret-handling obligation was lost.**

- **Rebuild-not-repair gap:** two-sided. Availability: during rebuild, new logins and new token issuance fail — bounded for existing work (tokens ≤900 s, in-flight payments unaffected, SSO cookie may re-auth after the rebuild), unbounded in duration because there is no SLA. Security: there is no bounded remediation window for a vulnerability in the publicly reachable identity root; "we rebuild with a newer release when we choose to" is precisely the K-2 acceptance, and the accepted residual is that this root sits on the public Internet while patching is discretionary. This review restates that residual and does not re-litigate it. The rebuild process itself (fresh image digest, fresh database, realm import, key registration, client verification) is designed but never exercised — the rev2 open items "boot-time realm import on upgrade" and "digest-pinned image" carry forward effectively unchanged; note also that §4.1's verify step ("register public keys, verify that each client can obtain a token") is the only test gate named, with no negative-case equivalent.
- **Secret handling: nothing quietly lost.** K-2's own record explicitly preserves "the obligation to keep secrets out of state and logs", and rev4 §4.3 restates the full set: assertion private keys, database password, bootstrap admin credentials, demo user password, all tokens, non-public registry values — with the concrete prohibition list (state, plan output, CI artifacts, images, task definitions, logs, access logs including `Sec-WebSocket-Protocol` and `Authorization`, static bundle) and the sharp observation that a secret leaked into *configuration* would be re-created forever by the rebuild model. The only control from rev2 §2.8 that disappears is backup/PITR/restore rehearsal, and that disappearance is deliberate and documented (D-9), not silent. One consequence worth recording: with backups removed as a recovery path, the *configuration source of truth itself* (repository, Terraform state, realm import artifact) becomes the sole recovery substrate — its integrity is load-bearing. §7.4 carries the S3 state backend protections (lockfile, versioning, SSE-KMS, Block Public Access) unchanged, which covers this; the dependency is now stricter because there is no second copy.
- **Bootstrap admin note:** "used once, then discarded with the container generation" must recur at every rebuild, and with no on-call there is no fast human response to a leaked bootstrap credential between rebuilds. Minor, consistent with K-2; no separate finding.
