### N-01 Auxiliary-window origin/source/state/COOP design — IMPORTANT → **CLOSED AS DESIGN TEXT; realization NOT CLOSED**

Rev2 confirmed an under-specification with security consequence: the dual-token flow's "second top-level redirect" was incompatible with memory-only custody (a top-level navigation destroys the SPA's in-memory token and pending state/PKCE verifier; recovery paths invite persisted bearers or a combined token).

The rev3 packet adds `browser-flow.md` (inside the 21-file verified packet), which supplies exactly the correction my rev2 retest criteria demanded, and I read it in full. Verified properties: the original HTTPS SPA owns both resource tokens, all flow records and all verifiers **in runtime memory only**; login runs in fresh auxiliary top-level windows while the SPA never navigates; independent cryptographically random state/nonce/PKCE-verifier per attempt and per resource, with interactive replacement after `login_required`; the pending flow record is bound to exact child WindowProxy reference, exact callback origin/path, issuer, client, resource, redirect_uri, SPA session epoch and a 120-second deadline; serialized flows; explicit bans on localStorage/sessionStorage/cookie/IndexedDB/service-worker/window.name persistence and on verifier/bearer in logs; the callback page holds no token custody, posts to its opener with the exact configured origin (never `*`), rejects an absent opener, and never recovers through persistent storage or broadcast channels; the parent accepts only exact `event.origin` **AND** `event.source === retained WindowProxy` AND an exact closed schema, atomically consumes the pending state before any exchange (replay cannot start a second exchange), and validates issuer metadata, signature/alg/kid, nonce, aud/azp and token resource rules; WS flow runs separately with `prompt=none`, `login_required` retires it, and no automatic purchase action exists; lifecycle covers closure/timeout/cancellation, bfcache/Back (fresh login forced, authority not resurrected), logout (issuer logout attempted, network failure shown, not claimed as revocation); failure paths assert token-installed=0, financial-sends=0, claims=0, automaticPaymentPosts=0.

The packet also states an explicit **opener/COOP feasibility gate** (`same-origin-allow-popups`, no `noopener`/`noreferrer`, issuer COOP must preserve the opener relationship, headers recorded on every leg, no silent weakening of issuer headers) and a required real-browser negative list (wrong origin, wrong source window, wrong/stale state, epoch expiry, nonce/verifier failures, code reuse, duplicate parameters, popup denial, severed opener, unsolicited callbacks, unexpected refresh token). This overrides the conflicting same-window wording everywhere in the composed packet, which is the correct precedence direction for a security control.

### N-02 Direct custom-domain bypass of the edge rate bound — IMPORTANT → **PARTIAL (endpoint half corrected; custom-domain residual OPEN, owner decision required)**

**Authored correction verified in bytes (default-endpoint half):** `modules/api/main.tf` sets `disable_execute_api_endpoint = true` on the console HTTP API and adds a dedicated `aws_apigatewayv2_domain_name` + `aws_apigatewayv2_api_mapping` to `$default`; `envs/stack/main.tf` wires the CloudFront `/api/*` origin to `module.api.origin_domain_name`; `envs/stack/dns.tf` authors the `api_fqdn` alias; `api_fqdn`/`api_certificate_arn` are new required inputs failing closed (FQDN validation; `api_fqdn` additionally rejects any `execute-api` substring); `modules/console/variables.tf` validates that the origin is not an execute-api host; `tools/policy_checks.py` check 13 (`api-default-endpoint`, `origin-execute-api`, `origin-custom-domain`, `origin-domain-missing`) machine-asserts the shape; the old `console_api_endpoint` output advertising the execute-api host is replaced. The compensating controls survive: the JWT authorizer (issuer + audience, `Authorization` identity source, no anonymous path) applies identically on the custom domain, and stage throttling remains.

**Residual (NOT CLOSED, confirmed structural):** `api_fqdn` is a public Route 53 alias to the API Gateway regional endpoint. A caller resolving it directly still bypasses the CloudFront edge entirely — the per-IP `/api/*` WAF rate bound, the managed rule groups and the response-header policy do not apply on that path. Unauthenticated abuse is denied by the JWT authorizer (with per-request authorizer-evaluation cost at API Gateway), but an **authenticated** holder of the single demo principal can evade the rate bound and other edge controls. This is a confirmed property of the authored topology, not a hypothesis.

**Closure options compared (commissioned):**

| Dimension | **Option A — REST API + regional WAF on the stage** | **Option B — origin-verification header (CloudFront `custom_header` + fail-closed boundary check)** |
| --- | --- | --- |
| Authorizer / JWT custody | HTTP API→REST conversion loses the native JWT authorizer (REST has no arbitrary-issuer JWT authorizer); token validation moves into a Lambda REQUEST authorizer — **K1-owned code at the authentication boundary**, widening exactly the surface C-03 already flags | Native JWT authorizer kept unchanged; enforcement is one fail-closed header check at the K1/H1 application boundary (claim-level checks are already application-owned there) |
| State / secret custody | No new secret | One high-entropy value: must be Terraform-generated (`random_password`), state-only (encrypted S3+KMS backend), never in `.tfvars`/CI variables/logs; access-log formats must exclude it (new policy check) |
| Rate-bound / edge-control coverage | Complete and structural: a stage-attached WAF covers direct `api_fqdn` traffic regardless of hostname; WAF telemetry covers direct attempts | Complete **conditionally**: direct traffic is rejected at the boundary; no WAF telemetry on that path (API/app logs become the abuse signal); relies on CloudFront overriding viewer-supplied same-name headers and on the value not leaking |
| Vendor support | DevOps verified (dated 2026-11-23 doc fetch) that WAF attaches to API Gateway **REST** APIs only, not HTTP APIs; I did not independently re-confirm that page and treat it as DevOps-verified recorded evidence | Verified by me against public docs (fetched 2026-11-24): CloudFront overwrites a viewer-supplied same-name custom origin header before forwarding, and "respond only when the request includes a custom header added by CloudFront" is the vendor-documented anti-bypass use case |
| Logging | WAF logs include direct attempts | Direct-path denials visible in API/access logs only; header redaction mandatory |
| Cost | REST request pricing above HTTP API + WAF web ACL/rule charges | ~zero recurring; no new artifact if enforced in the application boundary, or Lambda-authorizer invocations if a dedicated authorizer is chosen |
| Blast radius | Largest: API-type conversion + authorizer replacement at the auth boundary + full re-review of the console ingress; risk of new defects in newly app-owned token validation | Smallest authored diff; failure modes are silent (value leak, mis-scoped check) and must be pinned by policy checks and the contract |
| Fail-closed | Structural (attachment is configuration; default action denies) | Yes, but only if the contract specifies reject-on-absent/mismatched header and the check cannot be bypassed by header omission |

**Recommendation (smallest compliant option): Option B**, conditional on four mandatory constraints: (1) the header check is fail-closed on absent/mismatched value and is specified in the contracts before construction (a bounded contract delta — Requirements-owned); (2) the value is Terraform-generated, state-only, excluded from tfvars/CI variables and all log formats, with a new `policy_checks.py` assertion; (3) the header name avoids the CloudFront custom-header denylist and any header the application treats semantically; (4) direct-path denials are logged and observable. If the secret-custody condition or the enforcement placement fails independent review, **Option A is the indicated fallback** and remains the structurally stronger closure. A third configuration-only closure does not exist in this topology: regional WAF is unavailable on HTTP APIs (DevOps-verified) and CloudFront cannot present a client certificate for origin mTLS (provider schema, DevOps-verified).

**Decision ownership, stated plainly:** choosing Option A, choosing Option B with its conditions, or explicitly accepting and documenting the residual is an **architecture-owner decision for Fernando** (Human Solution Architect). It is not the Security reviewer's, DevOps's or Implementation's to make; the rev3 domain review independently identifies it as a human-only input. **I do not accept the risk on his behalf.** The residual remains IMPORTANT/OPEN until his disposition is recorded in the work item with owner/date/rationale/exact finding and revision, and the selected closure (if any) passes independent re-review. Retest criteria: post-deploy negative — direct `execute-api` host refused; per the selected option, either direct `api_fqdn` traffic WAF-covered (A: WAF logs show it) or rejected at the boundary (B: logged denials, header value absent from every log); forged unauthenticated request receives the exact contract error body (N-03 semantics).
