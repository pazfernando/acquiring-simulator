## 3. Q1 — Does the contract delta implement the four binding conditions exactly?

**Yes.** Judged against the four conditions as I recorded them (`f5696ed9…`, §4/N-02 recommendation) and as carried verbatim into the owner decision:

1. **Fail-closed specification before construction.** Delta §5.2 defines an exhaustive closed set — `ABSENT`, `EMPTY`, `DUPLICATE` (two occurrences, the payload-v2 comma-coalesced form, or case-differing map entries), `MISMATCH` — all four mapping to REFUSE, with `VERIFIED` as the only continue outcome. No partial acceptance, no log-and-continue, no relaxation flag (§5.2 closing, §6.1 "no bypass switch"). Initialization fails hard on a missing/short/malformed `EDGE_ORIGIN_VERIFY` (§5.3, OV-15): no silent default, no degraded mode. Constant-time comparison over the full value with an early length failure is specified in §5.2; the length (48, §8.1) is public contract knowledge, so the length-fast-path discloses nothing. The classification edge cases are security-conservative and coherent: whitespace-padded correct content is `MISMATCH` (never trimmed permissively), duplicate-name-spellings cannot defeat the single-value rule, and the comma rule is sound because the value alphabet is alphanumeric-only (a comma can only be coalescence). Placement is before **every** business action including the route's own 404/405 handling (§6.1–6.2), and a refusal consumes no rate-limit token, reads no registry, writes nothing (§11 zero-effect invariants). Independence from the JWT authorizer is stated precisely (§5.4): platform ordering unchanged, the gate reads only the header and the configured value, remains effective if the authorization is changed or a route is added (OV-17), and is explicitly not an authentication factor.
2. **Exact error code and status.** §7: `403`, code `EDGE_ORIGIN_NOT_VERIFIED`, byte-exact D-6-shaped body, one code for all four reasons, no echo of value/length/hash/reason, no CORS allowance, platform 401 bodies untouched, C3 envelope deliberately not reused — all correct.
3. **Header name justified against the denylist and semantic use.** §4.1 re-verified the CloudFront custom-header denylist against the vendor page (archived capture in `commands/09`, digest recorded; the denylist content matches the denylist I compiled in the prior review); §4.2's semantic-exclusion table covers every semantically treated header in the application (`Authorization`, C1/C2/C4 carriers, identity-assertion refusals, WS token carriage, `Origin`, tracing proxies, the D-5-forbidden `X-Demo-JWT`). `X-Origin-Verify` is denylist-safe and semantically unused. §4.3 correctly restricts injection to the origin `custom_header` and forbids every viewer-side evaluation point.
4. **Custody and log-exclusion rules.** §8 fixes generation (stack root, ≥256 bits, fixed length, closed token alphabet), storage semantics (encrypted S3+KMS state; the two provider-owned runtime copies declared bounded rather than denied — dispositioned in §5 of this report), exclusions across tfvars/CI/outputs/artifacts/plan/log formats/ADOT/responses, and fail-closed coordinated rotation (§8.4, OV-19). §10 specifies the observable direct-path denial: one structured record with a closed field set, dimension by reason, metric name fixed, forbidden fields enumerated, and the decision never dependent on logging success.
5. **Observable direct-path denials.** §10 correctly identifies the application record as the primary (only discriminating) signal, with the access log as corroboration, and defers alarm thresholds to a deployment input rather than inventing a number.

The delta also preserves the inherited-contract precedence rule (boundary clause governs only pre-business refusal), keeps OV-03 honest (unauthenticated direct requests produce the platform 401 and **no** denial record — the gate is not an unauthenticated control, which matches the finding's class: an authenticated holder of the demo credential), and its §12 list is a complete, correctly-scoped statement of what remains unproven. **No defect found in the delta.** One documentary nuance, not a defect: §5.2's EMPTY rule makes OV-05 (whitespace-only) classify as `EMPTY` while whitespace+padded-content is `MISMATCH`; the branch is unobservable to the caller because responses are byte-identical across reasons.

## 6. Q4 — Custody widening: disposition

The mechanism the owner selected cannot exist without two provider-owned runtime copies: the CloudFront origin configuration (`custom_header` value) and the console Lambda environment (`EDGE_ORIGIN_VERIFY`). Requirements declared this in delta §8.2 rather than hiding it; DevOps implemented it and asked for explicit reviewer acknowledgment.

**Disposition: (a) within the original condition's intent and acceptable.** Reasons, stated plainly:

1. The condition's "exists only in encrypted remote state" was written to forbid the value in **committed or configured artifacts of the delivery pipeline** — tfvars, CI variables, secrets stores containing literals, artifacts, logs — every one of which is authored-out and machine-asserted. It was not physically satisfiable as "the value exists nowhere else at runtime": the option I recommended (fail-closed comparison at the application boundary) necessarily implies the console Lambda receives the value as runtime configuration, and the recommended `custom_header` mechanism necessarily implies the value in the distribution configuration. The enforcement I specified and the custody I bounded were always going to produce exactly these two copies.
2. The bounding control the delta names is present in the authored shape: **no runtime principal can read either copy.** The console Lambda role's policy grants logs and the three DynamoDB scopes plus the guardrail only — no `lambda:GetFunctionConfiguration`/`GetFunction`, no `cloudfront:*` (verified in `modules/api/main.tf` and `modules/identity/main.tf`). The only in-account principal with the read surface is the deployment role, whose broad `lambda:*`/`cloudfront:*` is pre-existing state unchanged by this delta, bound by the exact-string OIDC subject condition (policy check 6) and already covered by the standing C-01/SR2-01/02 executed-IAM-negative evidence gate. Break-glass access is an operations fact outside this tree and remains where the prior review already placed it.
3. This interpretation is recorded here for traceability. It does **not** require a new owner decision, because the alternative — insisting on literal "state-only" — would render the owner's selected option mechanically impossible and force the unselected Option A. Should Fernando prefer the literal wording anyway, that is his option to exercise; I note only that it would reopen the option choice.

Residual, honestly stated: a deployment-role compromise reads the value. That residual is the deployment role's existing blast radius (it can also read every other state-carried secret, given state custody), not a new class introduced by this delta. It stays governed by the standing C-01 gate at the implementation review.
