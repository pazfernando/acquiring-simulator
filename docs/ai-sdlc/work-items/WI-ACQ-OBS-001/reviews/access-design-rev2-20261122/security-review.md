## Q1 — Owner decisions and ADR alignment

Answered: **not fully satisfied**. Keycloak replaces Cognito/managed-provider uncertainty; S2/S3 retain Gateway mTLS plus issued OAuth tokens; GitHub OIDC, us-east-2 and on-demand direction are retained without invented business quotas. S5 is explicitly withdrawn in §4 and §8; S5i has no HTTP route or OAuth evidence client. Accepted notification-only WebSocket TLS exception and token-expiry lease are correctly retained. However §5 incorrectly grants ACL_AUTH instruction-attestation signing authority: the assessment §4 records that this role has no C4 signing row. §4.1 also assumes the shared Lambda handler can obtain the invoking principal from invocation context; assessment §2 demonstrates that ordinary Lambda Context does not provide it. Cursor lifetime measured from minting need not equal the remaining token lease, contrary to §3's equality claim. Owner choices need not be reopened.

## Q3 — Trust boundaries and privilege escalation

Answered. The intended P-DEMO, P-SVC, P-TLS, P-AWS and P-EVID planes are explicitly distinct (v1 §2 retained by rev2 §2.9). Certificate fingerprint, OAuth client, environment, ACTIVE registry status, route/scope and synthetic-context mandate must all converge at the final authorization point. Signatures bind evidence rather than authorize transport; a network countersignature must not replace issuer proof. No implemented separation is certified: current transport context holds only environmentId/authenticatedSender and cannot carry the required certificate/client/registry binding.

Independent source inspection confirms C4PrincipalRole gives ACL_AUTH no evidence-signing authority, C4AuthenticatedTransportContext has two bounded 64-character fields, and C4KeyRegistry diagnosticForwardPermitted defaults to false and grants no signing/payment/receipt authority. SignedEvidenceAdmissionService rejects a transport sender unequal to the DIRECT signer or relay principal, explicitly rejecting diagnostic forwarding. Thus F1/F2/F3 are concrete design/composition gaps. Abuse hypothesis: manufacturing the absent invoker identity from payload, or bypassing signature verification to enable diagnostic forwarding, could make the handler a confused deputy accepting another principal's proof/context. No such bypass was executed or shown active. Preserve proof validation plus exact environment/principal/acquirer permission; do not treat diagnostic delivery as authority over outcomes or receipts.

The presenter relay remains a privileged deputy for console writes, gated by separate demo login and server-side mandate. Its loopback Host/Origin/CSRF/session controls are appropriate obligations, not tested protection. Rev2 §2.6/§10 says a lost relay key has 'no payment authority'; that is too absolute: it has no C4 outcome-signing authority, but console.write can initiate synthetic authorization when combined with a valid demo context (F7). A stolen service key alone must not bypass demo login. Reconnect and notification clients must never dispatch payments.

## Q4 — Key and secret custody

Answered. State design is adequate in direction: environment-separated S3 keys, us-east-2, SSE-KMS, versioning, Block Public Access, account allowlist, TLS-only access, separate bootstrap and S3-native use_lockfile with a compatible Terraform version. Lock-object delete rights must not imply state-delete rights. State is still sensitive even when private key generation/injection is excluded; schema §1's 'state is the only artifact Terraform writes' is false (plans/logs may also contain sensitive values). Verify all persisted derivatives, not just state (F8). No backend or lock contention check was run.

Client assertion, TLS and Ed25519 keys are separated, out-of-band generated, injected by scoped SSM/KMS or presenter-local owner-only file, and prohibited from Terraform/Git/artifacts/browser/logs. Those are implementation-time checks, including exact IAM/PassRole/OIDC subjects, masking, cold-start/versioned rotation and cleanup. Uploaded client-key rotation with overlap requires capability evidence; a single uploaded credential must not be presumed to support concurrent keys. A client-side jti cache cannot prevent a stolen assertion being replayed directly against Keycloak: token-endpoint enforcement must be demonstrated (F9). Keycloak not-before policy also requires API-side enforcement; offline JWKS signature checking alone does not convey a newly changed not-before timestamp.

**Design custody gap F10:** rev2 §2.6 describes OAuth client assertion keys, §9.3 covers DB/admin bootstrap secrets, but neither defines custody of Keycloak's own realm token-signing private keys. 'Private keys never enter Keycloak' can only mean client assertion keys; the realm signer necessarily exists there or in an explicitly integrated signer. Specify generation, active/passive key rotation, issuer JWKS overlap, encrypted DB/backups/export handling, authorized operator/runtime access, revocation distribution to offline API verifiers and restore/rollback behavior. A secret-free realm import is not proof of a secret-free realm backup. Keep realm signing keys separate from all C4 keys.

Presenter-local relay key risk is explicitly acknowledged and needs accurate blast-radius language (F7), local provisioning/permissions/removal evidence and narrowly scoped clients. Evidence private keys belong only to the processor/network/issuer signer, not ACL_AUTH, the console relay or diagnostic forwarder. The production public-key registry adapter and admission composition remain unbuilt; no evidence-key custody implementation is verified. F10/F9 are design gaps; actual secure storage, policy enforcement, rotation and leak checks remain implementation-time obligations, not demonstrated exposure.
