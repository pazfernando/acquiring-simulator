## Q2 — Self-managed Keycloak

**Verdict: PARTIALLY ANSWERED.** Hosting and configuration intent are concrete; no instance/realm/listener/key rotation or restore was exercised.

- **Realm/client configuration (§2.5):** one `acq-<env>` realm, registration and password grants disabled, public demo client with authorization-code/PKCE; three confidential service clients with service accounts, Signed JWT/RFC7523, RS256, registered public key and no retained client secret; explicit audience mappers and scoped tokens ≤900 s. This can express private_key_jwt in principle. Discovery is server-wide capability information, not proof that a particular client rejects secret authentication. Verify the pinned release's per-client authenticator and negative secret/no-assertion grants. Client assertion signing and issuer access-token signing are separate keys/algorithm decisions; Gateway's RSA access-token limitation does not itself require RS256 client assertions. Verify exact audience, iss/sub/client binding, alg/kid, time/skew and selected replay rejection across replicas. No client-registry/token-acquisition/relay implementation is certified.
- **Admin reachability (§2.4):** proposed ALB host/path allowlist and default deny should block `/admin/`, master realm, health/metrics/root. That is a proxy control, not physical absence: private task 8080 still serves the application/admin plane behind the ALB. A single catch-all/default-forward or higher-priority listener rule can expose admin paths without moving the task. Missing admin DNS is not protection against the existing public host/path. Test exact/prefix/normalized-path variants and host selection, review effective listener ordering/default action, and prevent direct task ingress. No present endpoint is proven unreachable. Public OIDC wildcard allows more than token issuance; constrain required methods/paths and rate-limit both unauthenticated and authenticated abuse.
- **Private placement/administrator (§§2.3–2.4/9):** Fargate task and Aurora private; SG admits ALB/operator path; TLS to DB verifies server; ALB-to-task HTTP is plaintext within VPC, a residual relative to fully encrypted hops. SSM forwarding to the actual Fargate task/operator-only equivalent is explicitly unverified, not an available runbook. Do not open public admin to resolve it. Define named administrator, least-privilege session/IAM access, bootstrap removal, audit and recovery path. Forwarded headers must be overwritten and trusted only from the proxy; changing hostname alone does not isolate admin REST.
- **Operations (§2.8):** digest-pinned image, monthly patch/redeploy, rehearsed major migration; Aurora backup/PITR (proposed seven days), secret-free boot-time realm configuration, DB restore plus realm/client validation. Boot-time import is reproducible configuration, not a substitute for a consistent database/keys backup. Product owner accountable and DevOps authors runbook; named operational executor, schedule and restore evidence remain absent. K-1 single task/no HA, K-2 operations and K-3 presenter-key residual remain proposed dispositions (§13), not individually accepted merely because Keycloak was selected.
- **Custody (§§2.6/9.3–9.4):** out-of-band assertion private keys in scoped SecureString/KMS or presenter owner-only file; public keys only in Keycloak. Separate TLS, assertion, access-token issuer, C4 and DB/admin credentials. Read-on-cold-start secret injection needs reload/rolling restart and verification of retired warm instances during rotation. A static uploaded key swap is not evidence that two assertion keys can be accepted concurrently on the selected Keycloak client; test actual dual-key support, or define a reviewed JWKS realization.
- **Rotation minimum:** rev2 §2.6 has **no concrete minimum overlap**. Carried v1 §3.3 and §13/configuration-schema still specify ≥24 h; therefore the total bundle is ambiguous, not proof the old minimum was formally removed. The replacement paragraph omits a material control and must explicitly preserve or deliberately replace it. Keep assertion-key overlap separate from issuer JWKS overlap; a Gateway key cache concerns issuer access-token public keys, not assertion public keys registered at Keycloak (Q5).
- **Revocation (§2.6/§12.4):** client disable stops new issuance; realm/client not-before does not magically update a locally validating Gateway or authorizer. `nbf` in an old signed token is immutable. Online not-before/status knowledge or current registry denial must reach every authorization/fanout point. JWKS removal is neither immediate revocation nor a per-client switch; cached signing keys and stateless tokens may remain usable until expiry/cache convergence. TTL-0 authorizer result caching does not eliminate JWKS or registry caching. Registry deny with bounded fresh reads and fail-closed failures is required; current WS revalidation is unbuilt. Q4 corrects the claimed current caller-cache behavior.
- **Availability (§2.8):** one task/DB/issuer is a new authentication availability dependency. Existing unexpired tokens can permit new work for their remaining validity (≤900 s), if local verification/current registry permits and required JWKS is cached; new issuance fails immediately. Missing JWKS or newly created clients can fail sooner. After token expiry, new payments cannot authenticate. Already-authorized/in-flight payment work and internal C4 late admission must not call Keycloak or resend. A WS reconnect now requires issuance, so outage removes observation renewal too. No HA or availability measurement was supplied.

**New single point of compromise:** Keycloak admin/runtime and its database/issuer signing material form a central identity root: compromise can mint/modify service and demo identities across this environment. Local relay-key and CI/bootstrap/DB credential compromise are additional paths, not owner-accepted waivers.

## Q3 — Internal-only late evidence

**Verdict: NOT ANSWERED as an implementable authenticated-sender mechanism; confirmed IMPORTANT design defect SR2-01.** Internal-only intent is clear and matches CA-1; the shared-function identity assertion in rev2 §4.1/§8 S5i is not implementable as written.

### Independently verified AWS semantics and field capacity

Official AWS Java context documentation (HTTP 200, 2026-11-22T23:36:54Z, not truncated) defines `getInvokedFunctionArn()` as “Returns the Amazon Resource Name (ARN) that's used to invoke the function. Indicates if the invoker specified a version number or alias.” Its example is the **target Lambda function ARN**. It is not the caller's IAM principal ARN. `getIdentity()` is mobile Cognito identity, and `getClientContext()` is client-provided mobile context, neither a trusted direct-invoke IAM role accessor. See https://docs.aws.amazon.com/lambda/latest/dg/java-context.html. AWS authorizes Invoke at the service boundary but does not automatically pass that authenticated principal into this Java handler. STS GetCallerIdentity from inside the handler would identify the handler's own execution role, not the invoker; it was not called.

AWS IAM identifiers documentation explicitly gives `arn:aws:iam::<account>:role/<role-name-with-path>` and STS `arn:aws:sts::<account>:assumed-role/<role-name>/<role-session-name>` (HTTP 200, fetched 23:36:54Z; returned page truncated after 20,000 chars, cited syntax appears before truncation): https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html. IAM quotas give role name ≤64 chars, role session name ≤64 and path ≤512 (HTTP 200, 23:36:55Z, not truncated): https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html.

**Precision correction:** AWS ARNs are not universally >64 chars. A one-character role in a synthetic 12-digit account yields 32 chars; a legal 64-character role yields a **95-character** role ARN without any path; 64-character role plus session produces a **168-character** STS ARN. These are local string-length calculations, not IAM calls. All these role/session ARNs contain `/`. Current `C4AuthenticatedTransportContext.java:16–18` calls `requireId(...,64)`; `C4CarrierSchema.java:22,32–38` allows only `[A-Za-z0-9._:-]+`, excluding `/`. Thus even short role ARNs are rejected; many legal ARNs also exceed the length bound. Do not confuse the 64-char *role name* with total ARN length or invent a universal ARN maximum.

Widening the record cannot produce a missing principal fact. A trusted mapping must first derive a principal, canonicalize stable role identity versus STS sessions without accepting caller-selected labels, map to a profile-valid short sender id, then resolve environment/role/acquirer mandate/allowed key IDs. No implemented mapping or production registry adapter is supplied. Four role names do not confer authority: `ACL_AUTH` is not an evidence attestor; diagnostic delivery is a scoped permission and unchanged-proof forwarding only.

### Effective invocation boundary, not just route absence

- Rev2 calls SDK invocation “private” and proposes no VPC endpoint. Standard Lambda Invoke is an AWS HTTPS API; absence of a function URL/Gateway/custom DNS does **not** make Invoke network-private. A permitted role's temporary credentials used outside the account's workload/network may still invoke it. A compromised producer can also be an inside-to-outside confused deputy. This is a residual path for outside delivery with authorized/stolen AWS authority, not demonstrated anonymous public evidence submission.
- AWS IAM policy evaluation explicitly combines same-account identity and resource allows by **union**; absence from a resource-policy Allow list is not a Deny against a separately allowed same-account identity. Official source (HTTP 200, 23:37:02Z, not truncated): https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html. Therefore §4.2(1)'s guarantee that *every* unlisted role is denied before the handler solely because it is absent from the resource allowlist is incorrect (IMPORTANT SR2-02). Evaluate all identity grants, role-assumption trust, permissions boundaries/SCPs where applicable, qualified/unqualified function resources and aliases. Use a supported effective restriction/deny strategy, not an assumed allowlist intersection.
- `aws:SourceArn`/`SourceAccount` are source-service context controls for service-to-service calls, not reliable direct SDK invoker provenance. Requiring absent condition keys may deny all intended direct calls; permitting their absence does not authenticate a sender. Document actual request-context availability and the direct producer principal restriction. No policy was changed or simulated here.
- Current `infra/template.yaml:47–113` has one HTTP authorization route and no authored late function/URL/route. That supports “no late endpoint in this template,” **not** an account-wide deployed absence claim. No deployed mappings, external role trust or IAM inventory was provided; an actual outside-submission path is **not established**, and its absence is **not proven**.

**Minimal correction:** select one reviewed mechanism, e.g. producer-specific function/qualified alias with effective exclusive invoke authority and a trusted target-to-sender mapping, or an authenticating internal broker forwarding independently authenticated provenance. Aliases are client-selected targets and work only if other producers/unqualified paths cannot select them. Do not trust payload/header `sender` or ClientContext; do not remove independent C4 signature/key/role/hash/business-version checks to work around missing transport identity. Maintain atomic admission and no resend.

**Retest to close SR2-01/02:** static target-to-principal/key-id matrix and effective policy evaluation; separately authorized invokes as each legitimate role, another allowed-to-invoke same-account role, unauthorized assumed session, foreign account and role used outside intended network; wrong target/alias, spoofed payload sender, diagnostic role/key swaps and C4 tampering; verify no handler execution on rejected invocation, unchanged-proof forwarding only, exact atomic business/evidence/event behavior and zero financial redispatch. No such check ran here.

**Residuals:** producer compromise/credential theft still requires independent C4 proof and correlation, but can replay/abuse admission resources; identity isolation and network-origin restriction are different controls. **Missing evidence:** implementable provenance, effective policies, production key registry, late handler/atomic wiring and deployed inventory. None is owner-accepted by CA-1.

## Q4 — Token-expiry WebSocket lease, reconnect and revocation

**Verdict: PARTIALLY ANSWERED; lifecycle guarantee remains BLOCKED by missing implementation/evidence.** With a service token valid ≤900 s and minted before connect, `min(jwtExp, connectTime+900s)` equals that token's expiry. Removing the dead 30-minute term does not lengthen credentials. Effective connection authorization must also end at the earlier demo-token expiry and any registry/mandate invalidation, not just service expiry. A 900-second *configuration* equality is not equality of all actual expiry instants.

**Availability/DoS residual:** expiry forces re-mint and connect/new epoch, introducing gaps, duplicate observation work, repeated authorizer/issuer/registry calls and catch-up load. Aligned client expiry can cause a thundering herd; reconnect faults/repeated expiry can amplify token issuance requests. WAF does not stop abuse by a permitted client. Carried O6 reconnect jitter helps but does not specify issuance retry bounds, single-flight token acquisition, backoff after issuer failure, per-client technical rate controls, dedupe or resumption under prolonged outage. Apply bounded jitter/backoff and concurrency at the relay/issuer without extending token validity or inventing financial business quotas. Shared Keycloak saturation can indirectly impair new payments, even though a missing socket must not gate an otherwise authorized HTTP payment. Never respond to socket failure/expiry/cursor refresh with payment retry.

**Independent source correction — there is no demonstrated cold-start caller-record cache:** both assessments, rev2 §3 and the supplementary report say `AwsRuntime.caller` caches the registry at cold start with no TTL. The current source contradicts that: `AwsRuntime.java:43` calls `registry(...)` each time; lines 28–32 perform `GetItem` with `consistentRead(true)`. `ProcessorHandler.java:35–38` calls that resolver for each matching request. The static DynamoHolder caches a **DynamoDB client**, not the caller row. The initialized service caches service/profile construction, not `CALLER#<subject>` lookups. This source was independently read, not inferred from test names. The reported source hash equals the assessment's own `AwsRuntime` input hash; this is an interpretation error, not evidence of changed source fixing a former cache. Current `AuthorizedContext` still has no credential status/version and no WS revalidation path. Fresh current HTTP lookup therefore does not establish WS revocation at all.

**Is ≤one heartbeat achievable?** In a future implementation, §3's ≤30 s opportunistic cache plus unconditional strong heartbeat/scope-change reads can bound detection near 30 s **only if a server schedules/checks idle connections, fresh decisions govern fanout, failed reads fail closed, and dispatch/close queues are bounded**. Client-triggered heartbeat alone cannot evict a malicious silent client. A ≤30 s cache by itself can combine with 30 s polling to approach 60 s if the heartbeat reuses stale data. The proposed unconditional heartbeat read avoids that specific additive delay, but network/scheduler/close time adds latency; “about one heartbeat” is not a measured hard ≤30 s guarantee. Stop query/fanout immediately at invalidation even if physical close/cleanup fails. Require revocation tests immediately before/after heartbeat/cache boundaries, silent-client/registry-failure/load cases and timestamped last-disclosure results. No such implementation/test is present; do not accept next-heartbeat revocation as delivered.

**Cursor re-mint:** rev2 §3 says reconnect and >900-second passes must re-mint; it defines no authenticated endpoint/operation, page-boundary continuation, snapshot preservation or bounded resync procedure. A cursor minted later than the access token need not expire when the socket does; the claim “always expired at lease end” is false without shared-expiry binding. O6 requires 410 RESYNC_REQUIRED on expired cursor/generation/revision and a new snapshot; retention-delta §3 says reissue creates a new snapshot, not extended old snapshot. New epoch/generation on reconnect also invalidates old bindings. Mid-pass “re-mint” must not silently extend an old snapshot or transplant it across generations. Specify an authorized new snapshot from a verified contiguous watermark with safe ranges, or author/review a distinct continuation contract; preserve H/R semantics, dedupe/merge and honest gaps. This is an additional contract gap, not permission to change the approved contract here.

**Residuals:** ≤15-minute bearer theft window absent current registry deny, reconnect/issuer availability, finite catch-up and shared-service saturation. **Missing evidence:** WS authorizer/routes/registry status/read/fanout scheduler, cursor/range read implementation and matching reviewed protocol, timestamped revocation/outage/long-pass tests. Owner D-D accepts weaker transport, not failure of its compensating expiry/revocation controls.

### Rotation control regression/ambiguity (SR2-03, ADVISORY)

V1 `design.md:72` required overlap at least Gateway JWKS cache plus margin, old published/non-signing key **≥24 h**; its §13 assertion-key row (`:230`) independently required credential overlap **≥24 h**. `configuration-schema.md:61` also required ≥24 h for `OAUTH_KEY_<CLIENT>`. Rev2 §2.6 substitutes merely “an overlap window” with **no concrete minimum**. However §§2.9/9 say prior settings/schema/key flow carry forward; the unchanged files still contain the numeric requirement. Therefore a control is **quietly omitted in replacement prose and precedence is ambiguous**, not definitively rescinded across the full bundle. Reinstate explicit ≥24 h or record a measured, independently reviewed replacement per key class. No owner decision authorized shortening it.

Do not copy the old rationale blindly: (a) assertion public keys authenticate clients at Keycloak and need issuer registration/JWKS/old signer convergence; (b) Keycloak issuer signing keys validate access tokens at API Gateway/authorizers and need their JWKS convergence plus outstanding token/skew horizon; (c) TLS truststore/certificate and C4 key rotations are distinct again. The supplementary review conflates (a) and (b). A Gateway's cached issuer key cannot extend an expired token; deleting an assertion key cannot revoke previously issued access tokens. Retest dual-key transition, stale signer/secret consumers and forced revocation independently for each class.

Other changed/ambiguous controls: native mTLS is explicitly absent only on WS (accepted, not quietly removed); withdrawing public S5 reduces exposure but replaces its transport identity with an unrealizable principal-context mechanism, not equivalent identity protection. No OAuth credential on an internal IAM-only seam is not itself a relaxation if effective identity/proof controls exist. The corrected WS lease removes a dead constant, not a genuine second security bound, but introduces the unfulfilled re-mint/resync obligations described in Q4. Rev2's broad “no payment authority” description of a presenter key must be narrowed: `svc-console-relay` has `console.write`, which can initiate an authorized synthetic payment through the required mTLS/demo/mandate checks. It has **no C4 evidence-signing or direct issuer-decision authority**; that is not the same as no payment initiation capability.
